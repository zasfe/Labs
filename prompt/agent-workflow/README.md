# playbook

버전 `1.2.0` — 프로젝트에 독립적인 작업 절차·구현 지침 묶음.

이 폴더의 **정본 위치**는 <https://github.com/zasfe/Labs/tree/master/prompt/agent-workflow> 하나다. 복사받는 쪽은 복사한 버전과 이 위치를 적용 문서 머리 기록란에 적는다. 이 문서는 복사본에서 고치지 않는다.

## 구성

문서는 층으로 나뉜다. 프로젝트는 공통 층과 프로필을 항상 채택하고, 언어·유형·환경 층은 해당하는 것만 채택한다. 폴더는 나누지 않는다 — 문서는 같은 폴더의 파일명으로만 서로를 가리킨다(아래 「무참조 게이트」의 링크 범주).

| 파일 | 층 | 내용 |
|---|---|---|
| `README.md` | — | 이 문서. 구성·읽기 순서·채택 절차·자리 이름 규칙·교훈 전달·갱신 규칙 |
| `CHANGELOG.md` | — | 버전별 변경 기록 |
| `workflow.md` | 공통 | 작업 절차(언어·빌드 도구·AI 제품 무관). dev 프로필 기준 |
| `profiles.md` | 프로필 | 작업 강도 프로필(dev·dev-fast·standard)별로 workflow.md와 다른 점 |
| `go.md` | 언어 | Go 구현 지침 |
| `go_httpcli.md` | 유형 | HTTP 요청 기반 클라이언트 구현 지침. 원칙은 언어 무관이고 Go 표기는 예시다. 실서버에 요청하는 모든 CLI에 적용한다 — 인증 없는 공개 API라도 응답 원문 열람 금지와 격리 시험은 적용 대상이다 |
| `env_docker_wsl.md` | 환경 | **선택 부록.** WSL2 + docker compose 실행 환경 지침. 그 환경을 쓰는 프로젝트만 채택한다 |
| `project_template.md` | 양식 | 프로젝트가 채우는 적용 문서 양식(머리 기록란·바인딩 표·프로젝트 예외·주요 변경 목록·근거 색인·문서 맵·결정 원장 양식·로드맵 최소 절·오늘할일 최소 절·설계 문서 최소 절·구현 위임자 정의 파일 최소 항목·진단 실행 표식 절). 원본 양식은 playbook 안에 그대로 두고 복사본을 채운다 |

새 문서를 더할 때의 파일명 규칙: 언어는 `<언어>.md`(예: `python.md`), 언어에 묶인 유형 지침은 `<언어>_<유형>.md`, 언어 무관 유형 지침은 `<유형>.md`, 환경 부록은 `env_<환경>.md`. 기존 파일명은 소비 프로젝트의 참조를 깨지 않도록 바꾸지 않는다 — `go_httpcli.md`는 내용이 언어 무관이지만 1.1.0의 이름을 유지한다. 다른 언어의 프로젝트도 이 파일을 채택하며, 그 안의 Go 문서 참조(HC-01의 격리 조건, HC-05의 golden 관리)는 자기 언어 문서의 해당 절로 바꿔 읽는다.

## 표준 읽기 순서

적용 문서, 진입 문서(`{ENTRY_DOC}`), 문서 맵은 모두 아래 순서를 따른다.

**규범 블록 — 규칙과 값을 읽는 순서**

1. 프로젝트 적용 문서(`project_template.md`를 복사해 채운 것) — 값과 예외
2. `workflow.md` — 절차
3. `profiles.md` — 적용 문서에 적은 프로필의 차이(dev면 건너뛴다)
4. `go.md` — 언어 문서
5. `go_httpcli.md` — 실서버에 요청하는 CLI인 경우
6. `env_docker_wsl.md` — 선택 부록, 채택한 경우만

**읽는 시점 규칙**

- 세션을 시작할 때는 아래 현황 블록을 읽는다.
- 규범 블록은 Task에 착수할 때 한 번 읽고, 이후에는 필요한 절·ID만 다시 읽는다.
- 결정 원장(`{DECISION_LEDGER}`)·설계 문서(`{DESIGN_DOC}`)·백로그(`{BACKLOG_FILE}`)는 항상 읽지 않고 **필요 시** 읽는다 — 위임 승인과 대조할 때, 중단된 작업을 재개할 때, 코드를 변경하기 전에.

**현황 블록 — 세션을 시작할 때 지금 상태를 파악하는 순서**

1. 오늘할일 기록(`{ORDERS_FILE}`) — 지금 무엇을 해야 하는가
2. 로드맵(`{ROADMAP_FILE}`) — 세션 시작 때 현황 파악용으로 읽는다. 전체 Task의 범위·의존·결과
3. 현재 단계 계획서
4. 직전 Stage 승인요약서

[workflow.md](workflow.md) §7의 컨텍스트 구성 우선순위와 위 현황 블록은 공통 부분(오늘할일 기록 → 현재 계획서 → 직전 Stage 승인요약서)의 순서가 같다. 로드맵은 §7의 「필요한 영구 문서」에 속하며, 현황 블록에서는 세션 시작 때 먼저 읽는 것으로 정한다.

적용 문서와 playbook이 다르면 **적용 문서가 우선한다.**

## 채택 절차

새 저장소는 playbook 복사본(1)만 담은 초기 커밋을 기준 브랜치에 두고, 2~5는 첫 정식 Task 안에서 수행한다(6이 그 Task가 만들 것이다).

1. 폴더 전체를 대상 프로젝트로 복사한다(선택 부록은 채택하지 않으면 빼도 된다). 문서는 폴더 밖 파일을 참조하지 않는다.
2. 적용 문서를 **playbook 폴더 밖**(예: `{DOC_ROOT}/spec/`)에 만든다. `project_template.md`를 그곳으로 복사해 값을 채우고, 바인딩 표식 주석 줄과 표 형식은 그대로 둔다. 원본 양식은 playbook 안에 그대로 둔다 — 이동하면 양식이 사라져 무참조 게이트가 대상 부재로 실패한다. 적용 문서를 playbook 폴더 안에 두면 복사본 갱신 때 덮어써지고 무참조 검사와 충돌한다.
3. 프로젝트 진입 문서(`{ENTRY_DOC}`)에 위 「표준 읽기 순서」를 넣는다.
4. 복사한 playbook 버전, 정본 위치(받은 출처), 적용 문서 위치, 제안 접수 창구를 적용 문서 머리 기록란에 적는다.
5. (권장) 프로젝트가 자기 고유어로 playbook 무참조 게이트(`{NEUTRAL_GATE}`)를 둔다. 검사 범주별 판정은 아래 「무참조 게이트」를 본다. 고유어 목록은 프로젝트의 것이므로 playbook에는 넣지 않는다.
6. **채택 직후 첫 정식 Task로 문서 골격을 만든다.** 만들 것: 적용 문서(값 채움 완료) · 진입 문서 · 로드맵(`{ROADMAP_FILE}`, 첫 Task 등재 때 `{ROADMAP_ENTRY_FORMAT}`을 정해 바인딩에 적고 이후 바꾸지 않는다) · 결정 원장(`{DECISION_LEDGER}`) · 설계 문서(`{DESIGN_DOC}`) · 쓰기로 한 게이트. 로드맵·오늘할일·원장·설계 문서의 최소 양식은 `project_template.md`에 있다.
   - 첫 Task는 절차 1 전에 Task 번호 표기(`{TASK_ID_FORMAT}`)·오늘할일 경로(`{ORDERS_FILE}`)·브랜치 패턴(`{BRANCH_PATTERN}`)을 정해 적용 문서 초안에 먼저 적는다.
   - 게이트·CI 골격은 이 첫 Task에 넣거나 별도 Task로 두며, 어느 쪽인지 적용 문서에 기록한다. `{TASK_CI_CMD}`가 아직 없으면 `project_template.md`의 `{TASK_CI_CMD}` 의미문에 있는 최소 검사 목록을 사람이 수동으로 확인하고 결과를 기록한다.

### 아직 정할 수 없는 값

값 칸을 비우면 게이트가 실패한다. 아직 정할 수 없는 값은 `미정 — <확정할 Task·절차>`로 적는다(예: `미정 — 첫 Task의 로드맵 등재 때 확정`). 빈 칸이 아니므로 게이트를 통과하며, 확정되면 그 값으로 바꾼다. 쓰지 않는 자리는 「없음」과 사유를 적는다. 의미문에 「(선택)」이 붙은 자리는 workflow가 선택 문서로 정한 것이라 쓰지 않으면 「없음」과 사유를 적는다.

## 무참조 게이트

게이트를 둘 때 범주별 판정은 다음과 같다. 대상 범위는 범주마다 다르다.

| 범주 | 판정 | 대상 |
|---|---|---|
| 고유어 | 프로젝트 자신의 고유어 정규식이 하나라도 일치하면 실패 | playbook 폴더 |
| 링크 | 인라인 링크의 대상이 같은 폴더 파일명(+`#앵커`)이나 `https://`가 아니라 폴더 밖을 가리키면 실패(예: 대상이 상위 폴더 경로면 실패, 같은 폴더 파일명에 `#앵커`를 붙인 것은 통과) | playbook 폴더 |
| 미정의 자리 | playbook에 쓰인 자리(중괄호 안이 대문자로 시작하고 대문자·숫자·밑줄로 된 2자 이상 — 예: `{DOC_ROOT}`)가 양식의 바인딩 표에 없으면 실패. playbook 폴더만 검사하며 적용 문서의 경로 표기는 검사하지 않는다 | playbook 폴더 |
| 바인딩 누락 | 양식의 자리가 적용 문서 표에 행이나 값이 없거나, 적용 문서에만 있는 자리가 있으면 실패. 적용 문서의 경로는 게이트 설정값(`{NEUTRAL_GATE}`가 읽는 경로)이다 | 적용 문서의 바인딩 표 |
| 대상 부재 | 검사할 폴더나 파일이 없으면 통과가 아니라 실패 | 위 전부 |

## 자리 이름 규칙

- 프로젝트마다 다른 값은 `{자리_이름}`(대문자와 밑줄 2자 이상)으로만 쓴다. 중괄호는 자리 전용이다.
- 경로·명령 안에서 상황마다 달라지는 부분(번호·날짜 등)은 자리가 아니라 꺾쇠 표기로 쓴다 — 예: `<N>`(Task 번호) · `<S>`(Stage 번호) · `<YYYYMMDD>`(날짜) · `<작업단위>` · `<Task ID>` · `<제목>` · `<상태>` · `<날짜>`. 꺾쇠 표기는 바인딩 표에 정의하지 않는다.
- 쓰는 자리는 모두 `project_template.md` 바인딩 표에 정의한다. 표는 `<!-- playbook-binding -->` 표식 바로 뒤의 표이며, 행의 첫 칸에 `{자리_이름}`을 적는다(의미 열은 생략해도 된다).
- 사람 결정권자의 역할 이름은 문서에서 「작업지시자」로 쓰고, 프로젝트가 다른 이름을 쓰면 `{HUMAN_ROLE}`로 바꿔 읽는다.
- 용어의 뜻은 [workflow.md](workflow.md)의 용어 표에 있다.

## 정본과 갱신 규칙

- playbook 정본은 **하나**다. 복사본에서 직접 고치지 않는다.
- 새 교훈의 전달은 아래 「교훈 전달」을 따른다.
- 복사본을 새 버전으로 갱신하는 절차: ① 폴더를 새 버전으로 교체한다(적용 문서는 폴더 밖이라 보존된다) → ② 적용 문서 머리 기록란의 복사한 버전을 갱신한다 → ③ MAJOR가 오르면 CHANGELOG의 삭제·의미 변경 항목을 읽고 적용 문서의 프로젝트 예외·값이 여전히 맞는지 확인한다 → ④ 게이트를 다시 실행한다. 양식에 자리가 늘거나 줄었으면 적용 문서 바인딩 표에 같은 행을 추가·삭제한다.

## 교훈 전달

프로젝트에서 얻은 교훈이 다른 프로젝트에도 적용되면 정본으로 올린다.

1. **받은 쪽(복사본 사용 프로젝트)**: 적용 문서 머리 기록란의 제안 접수 창구(정본 보유 쪽이 정한 제출 방법)로 제안을 보낸다. 제안에 적는 것 — 교훈 · 일반화한 문장 · 원 사례의 요지 · 영향받는 ID. 제안은 자기 백로그(`{BACKLOG_FILE}`)에도 기록한다(근거 색인에는 정본이 ID를 확정한 뒤에 적는다).
2. **정본 보유 쪽**: 제안을 검토하고, 일반화(고유 사례·이름·번호·경로·명령 제거)하고, [CHANGELOG](CHANGELOG.md)에 적고, 버전을 올린다. 반영은 [workflow.md](workflow.md) §6-1 WE-04의 승격 절차를 따른다.
3. 원 사례의 출처는 각 프로젝트의 근거 색인에 남기고 playbook에는 쓰지 않는다. 정본 보유 쪽은 반영 결과(새 ID·버전)를 제안한 프로젝트에 알리고, 받은 쪽은 새 버전으로 위 갱신 절차를 따른다.

## 버전 규칙

`MAJOR.MINOR.PATCH` — 규칙 추가는 MINOR, 규칙 삭제·의미 변경은 MAJOR, 문구 정리는 PATCH. 새 프로젝트는 복사한 버전을 적용 문서에 적는다. 버전은 [CHANGELOG](CHANGELOG.md) 최신 절이 정본이며 이 문서 머리의 버전도 함께 올린다. `-draft`는 확정 전 초안을 뜻하며 확정 시 접미를 뗀다. 1.0.0 이후에는 규칙 ID를 재사용하지 않고 폐기 표시만 한다(폐기는 CHANGELOG에 「폐기: ID — 이유」로 적는다).
