# HTTP 클라이언트 구현 지침

HTTP 요청으로 원격 서버를 다루는 CLI에만 추가되는 규칙을 담는다. [workflow.md](workflow.md)를 전제로 하며, Go 고유 규칙은 [go.md](go.md)에 있다. 이 문서는 **실 자격증명과 실서버가 개발 환경 가까이에 있다**는 점 때문에 생기는 규칙이다.

- `{자리_이름}`의 의미는 [project_template.md](project_template.md) 바인딩 표에 있고, 값은 그 양식을 복사해 채운 프로젝트 적용 문서에 있다. 용어(golden·sentinel 등)의 뜻은 [workflow.md](workflow.md)의 용어 표에 있다.
- 이 문서는 원칙만 쓴다. 선택 부록 `env_docker_wsl.md`를 채택한 프로젝트는 그 문서에 컨테이너·WSL 환경의 구체 설정이 있다.
- 체크리스트 ID(`HC-nn`)는 재사용하지 않는다.

## 1. 테스트 환경과 자격증명

- [ ] **HC-01 테스트와 위임자의 테스트 실행을 자격증명·네트워크가 없는 격리 환경으로만 시켰는가**
  테스트는 `{TEST_RUNNER}`에서만 돌린다(격리 조건은 [go.md](go.md) §1). 개발용 실행 환경 `{NET_RUNNER}`는 **실 자격증명이 주입될 수 있고** 네트워크가 열려 있으므로, 실제 세션이나 서비스를 배선하는 테스트가 거기서 돌면 **실서버로 요청이 나간다.** 격리 환경에서는 설정도 나갈 길도 없어 로컬 루프백 가짜 서버만 남는다. `{NET_RUNNER}`는 도구 내려받기처럼 네트워크가 꼭 필요한 정적 검사와 개발용 실행에만 쓴다. 위임 지시서에도 `{TEST_RUNNER}`를 **명시**한다.
  패키지별로 환경 절연 목록을 만들어 두었더라도 불완전할 수 있다. 새 배선 테스트의 접속 대상은 루프백(가짜 서버 · 닫힌 로컬 포트 주소)뿐인지 확인한다.
  <br>*사례 — 설정 읽기 계층이 프로세스 환경 변수를 테스트 대역보다 먼저 읽었다 → 다중 대상 배선 테스트가 개발용 환경에서 돌았고 실 자격증명이 주입돼 있었다 → 실제 서버에 조회 요청이 나갔고 응답(서버 이름·IP)이 에이전트 출력에 찍혔다. 격리 환경으로 옮겨 재발을 막았다.*

- [ ] **HC-02 개발용 실행 환경에서 프로세스 환경 변수가 파일보다 먼저 읽히는지 확인하고 탐침을 짰는가**
  설정 로더가 프로세스 환경 변수를 비밀 파일보다 먼저 읽는 프로젝트(`{SECRET_ENV_CONVENTION}`에 명시)에서, 개발용 실행 환경에 실 자격증명이 환경 변수로 주입돼 있으면 가짜 환경 파일을 지정해도 실제 접속 대상이 읽힌다. 이 환경에서 수동 탐침을 돌릴 때는 접속 대상 주소를 출력하는 명령(설정 목록 출력 등)을 쓰지 않는다. 비밀 환경 변수는 `{SECRET_ENV_CONVENTION}` 규약을 따르고 값은 출력하지 않는다.
  <br>*사례 — 개발 컨테이너에 실제 환경 파일이 환경 변수로 주입돼 있어, 가짜 환경 파일을 줘도 실제 접속 대상이 읽혔다.*

## 2. 실서버 확인은 사람만

- [ ] **HC-03 실서버 확인과 요청·응답 원문 열람을 에이전트가 하지 않았는가**
  에이전트는 실서버에 명령을 보내지 않고 **실서버 응답 원문을 읽지 않는다.** 에이전트가 읽은 내용은 모두 외부 AI 서비스로 전송되므로, 읽는 순간 원문이 밖으로 나간다. 실서버 확인은 작업지시자가 호스트에서 `{LIVE_CHECK_CMD}`로 한다 — 절차는 `{LIVE_CHECK_PROCEDURE}`를 본다. 에이전트가 받는 것은 작업지시자가 확인한 요약뿐이고, 확인 도구가 원문을 따로 저장하면 그 위치를 열지 않는다.
  확인 스크립트를 고치면 **실서버가 아닌 대상으로** 검증한다 — 가짜 실행 파일로 판정·누설 로직을 보는 자체 시험, 격리 환경에서 실제 실행 파일로 인자를 돌려 보는 검사(HC-04).
  <br>*사례 — 에이전트가 실행한 테스트가 실서버로 요청을 보내 응답 원문이 에이전트 출력에 찍혔다(HC-01의 사례). 그 뒤 실서버 확인은 사람이 스크립트로 하고 에이전트는 요약만 받도록 정했다.*

- [ ] **HC-04 외부 명령을 감싸는 스크립트를 실제 명령으로 인자 검사했는가**
  가짜 실행 파일을 쓰는 자체 시험은 **판정·누설 로직만 본다. 플래그가 실제 명령과 맞는지는 보지 않는다.** 외부 명령을 감싸는 스크립트는 실제 명령으로 인자를 돌려 보는 검사(격리 환경)를 함께 둔다.
  <br>*사례 — 가짜 실행 파일 기반 자체 시험은 모두 통과했으나 필수 플래그 누락 3건이 있었고, 작업지시자의 첫 실행 전에야 드러났다.*

## 3. 가짜 서버로 시험하기

- [ ] **HC-05 실서버 없이 표준 `httptest` 서버와 fixture, golden 비교로 시험했는가**
  검증은 실서버 접속 없이 한다 — 표준 라이브러리의 `httptest.Server`로 가짜 서버를 띄우고, 입력 fixture로 응답을 주고, 출력은 golden 파일과 비교한다. golden 파일 관리는 [go.md](go.md) GO-13을 본다. 접속 대상 주소는 HC-01의 루프백 조건을 지킨다.

- [ ] **HC-06 요청이 들어오는 모든 진입점이 같은 검증을 거치는가**
  진입점 목록에 프로젝트가 가진 **모든 진입점**(명령행, 있다면 서비스 계층·서버·다른 프로토콜 어댑터)을 올린다. HTTP 클라이언트에서는 한 진입점에만 검증이 빠져도 같은 입력이 원격 서버로 나가는 잘못된 요청이 된다.
  원리·방법: [workflow.md](workflow.md) §6-1 WA-05

- [ ] **HC-07 경계 계층의 회귀 테스트를 가짜 어댑터가 아니라 실제 서비스 구현에 연결했는가**
  HTTP 경계나 여러 진입점을 지나는 회귀 테스트는 가짜 어댑터가 아니라 실제 서비스 구현에 연결하고, 바깥 의존부(원격 호출부 등)만 대역으로 바꾼다.
  원리·사례: [workflow.md](workflow.md) §6-1 WA-20

## 4. 오류 문구와 비밀

- [ ] **HC-08 오류를 감쌀 때 그 문구가 어디에 저장·전송되는지 끝까지 따라갔는가**
  `fmt.Errorf("…: %w", err)`는 원문을 **그대로** 싣는다(`%w` 체인). Go의 `*url.Error`는 **요청 URL(접속 대상 주소)** 을, 파일 오류는 **절대 경로**를 담는다. 그 오류의 `Error()`가 **상태 파일·응답·로그**로 가는지 호출자를 끝까지 따라간다. 간다면 **고정 문구의 sentinel 오류**를 돌려주고 원문은 감싸지 않는다. 테스트는 가짜 표식(예: `SECRET-HOST-MARK`)을 심어 **저장된 쪽에 그 표식이 없는지** 본다.
  <br>*사례 — 새 오류가 원문을 감쌌다면, 주기적으로 실행되는 상태 기록 코드가 그 오류의 `Error()`를 상태 파일에 **저장**해 접속 대상 주소가 파일로 샜을 것이다(계획 점검에서 지적). 오류 둘을 고정 문구로 두고 누설 테스트로 고정했다.*

- [ ] **HC-09 자격증명·접속 대상은 규약된 환경 변수나 비밀 파일로만 두었는가**
  자격증명과 접속 대상은 `{SECRET_ENV_CONVENTION}`이 정한 환경 변수나 `{SECRET_FILE}`(gitignore 대상)로만 읽고, 소스·테스트 fixture·로그·오류 문구에 적지 않는다. 외부 API 키·자격증명은 출력하지 않는다([workflow.md](workflow.md) §10 「커밋 전 보안 검사」).
