# 작업 결과 기준 합의(ALIGNS.md)

작업지시자의 목표·우선순위·선호·제약·판단 기준은 프로젝트 루트의 `ALIGNS.md`에 둔다. 모든 Task는 이 문서를 참조해 **작업 결과의 기준**을 계획 단계에서 정하고, 결과를 그 기준에 대조해 보고한다. 이 문서는 [workflow.md](workflow.md)를 전제로 하며, 어느 작업 강도 프로필([profiles.md](profiles.md))에서도 적용한다.

- `ALIGNS.md`의 형식과 유지 방법은 공개 규약 ALIGNS.md(<https://github.com/hmmhmmhm/aligns.md>, MIT)를 따른다. 이 문서는 그 규약을 workflow 절차에 연결하는 규칙만 쓴다.
- 규약이 제공하는 `align` 스킬은 설치하지 않아도 된다. 설치한 프로젝트는 기준을 정리하는 대화(정렬 검토)에 그 스킬을 쓰고, 설치하지 않은 프로젝트는 이 문서의 절차만으로 `ALIGNS.md`를 읽고 적용한다.
- `{자리_이름}`의 의미는 [project_template.md](project_template.md) 바인딩 표에 있다. 파일명 `ALIGNS.md`는 외부 규약이 정한 이름이므로 자리로 두지 않는다.
- 체크리스트 ID(`AL-nn`)는 재사용하지 않는다.

## 1. 문서별 역할

| 문서 | 담는 것 |
|---|---|
| `ALIGNS.md`(프로젝트 루트) | 지금 유효한 목표·우선순위·선호·제약·판단 기준. 이 프로젝트에서 "좋은 결과"가 무엇인지 정한다 |
| `{AGENT_INSTRUCTIONS_FILE}` | 에이전트가 언제, 어떻게 `ALIGNS.md`를 읽는지에 대한 연결 문장만 둔다. 기준 자체는 옮겨 적지 않는다 |
| 적용 문서 · playbook | 절차와 프로젝트 값 |
| 수행계획서(`{PLAN_FILE}`) | 이번 Task에 적용할 기준(「작업 결과 기준」 절) |
| 최종 결과보고서(`{REPORT_FILE}`) | 기준별 대조 결과(「기준 대조」 절) |

- 안전 원칙(workflow.md §10의 보안·비밀 규칙, 되돌리기 어려운 작업의 사전 승인)은 `ALIGNS.md`로 완화하지 않는다.
- `ALIGNS.md`와 적용 문서·playbook이 충돌하면 에이전트가 임의로 한쪽을 고르지 않는다. 충돌 내용을 수행계획서에 적고 작업지시자의 결정을 받는다.

## 2. Task마다 하는 일

| 절차(workflow.md §5) | 할 일 | 기록 위치 |
|---|---|---|
| 4 조사 | `ALIGNS.md`를 읽고 이번 Task에 해당하는 항목을 고른다. Git을 쓰는 프로젝트는 직전 Task 이후 `ALIGNS.md`의 변경 이력을 확인한다 | — |
| 5 수행계획서 | 「작업 결과 기준」 절을 쓴다. ① `ALIGNS.md`에서 인용한 항목(절 이름과 요지) ② 이번 Task에만 쓰는 완료 기준 ③ 기준 공백, 즉 결과를 좌우하는데 `ALIGNS.md`에 없는 판단. 공백이 결과나 범위를 실질적으로 바꾸면 작업지시자에게 묻고, 그렇지 않으면 가정으로 표시한다. 이 절은 수행계획서와 함께 승인받는다 | `{PLAN_FILE}` |
| 9 Stage Summary | 기준과 어긋난 결정, 기준 공백 때문에 내린 판단을 적는다 | `{STAGE_SUMMARY_FILE}` |
| 11 최종 결과보고서 | 「기준 대조」 표를 쓴다: 기준 · 판정(충족·미충족·미검증·해당 없음) · 근거 | `{REPORT_FILE}` |
| 13 지식 승격 | 이번 Task에서 드러난 지속 기준 후보를 제안 목록으로 보고한다. `ALIGNS.md` 반영은 AL-05를 따른다 | `{REPORT_FILE}` |

- standard 프로필의 간단 작업처럼 계획서를 쓰지 않는 작업은, 착수할 때 해당 항목을 확인하고 결과 보고에 기준 대조를 한두 줄로 적는다.
- `ALIGNS.md`가 아직 없는 프로젝트는 아래 §4의 최초 작성을 먼저 한다. 그 전까지 진행하는 Task는 수행계획서의 「작업 결과 기준」 절에 「`ALIGNS.md` 없음」이라고 적고 ②·③만 쓴다.

## 3. 체크리스트

- [ ] **AL-01 Task 착수 때 `ALIGNS.md`를 읽고, 해당 항목을 수행계획서 「작업 결과 기준」에 인용했는가**
  기준을 계획 단계에서 적어 두지 않으면 결과를 본 뒤에 기준을 고르게 된다. 인용은 `ALIGNS.md`의 절 이름과 요지로 하고, 전문을 옮겨 적지 않는다.

- [ ] **AL-02 확정 기준과 가정을 구분했는가**
  `ALIGNS.md`에 있거나 작업지시자가 승인한 기준만 확정 기준이다. 에이전트가 세운 기준은 승인 전까지 가정으로 표시한다. 요청이 짧으면 기존 대화와 프로젝트 문서를 먼저 확인하고, 결과나 범위를 실질적으로 바꾸는 공백만 묶어서 묻는다. 이미 답한 질문은 다시 묻지 않는다.

- [ ] **AL-03 결과를 기준별로 대조하고, 미충족·미검증을 충족으로 쓰지 않았는가**
  판정 근거는 실행한 명령과 결과로 적는다. 시뮬레이션, 도구가 요청을 받아들인 사실, 실제 환경에서 관찰한 동작을 구분하고, 확인하지 못한 환경은 미검증으로 적는다.

- [ ] **AL-04 결과에 맞추려고 기준을 고치지 않았는가**
  기준을 맞추지 못하면 미충족으로 보고한다. 기준을 바꿔야 한다고 판단하면 그 판단을 별도 제안으로 올리고, 이번 결과의 판정에는 쓰지 않는다.

- [ ] **AL-05 `ALIGNS.md`는 작업지시자의 명시 지시나 확인이 있을 때만 바꿨는가**
  한 번만 적용하는 예외를 영구 기준으로 올리지 않는다. `ALIGNS.md`에는 현재 기준만 두고, 변경 이력은 Git 이력으로 대신한다. 별도의 정렬 기록 파일을 만들지 않는다. 마지막 전체 확인 시각(`Last aligned`)은 작업지시자가 문서 전체를 확인했을 때만 갱신하고, 일부만 확인한 내용은 해당 절에 확인 날짜와 「부분 확인」을 따로 적는다. Git을 쓰지 않는 프로젝트는 이력이 남지 않는다는 한계를 작업지시자에게 알리며, 요청 없이 Git을 초기화하거나 대체 이력 파일을 만들지 않는다.

- [ ] **AL-06 판단이 반복해서 어긋나면 기준 공백을 의심하고 정렬 검토를 제안했는가**
  중요한 결정이 작업지시자의 의도와 어긋나거나, 같은 종류의 수정 지시가 반복되거나, 다음 방향이 불분명하면 해당 기준을 정리하자고 제안한다(`align` 스킬을 설치한 프로젝트는 그 스킬을 쓴다). 명백한 실행 오류는 정렬 검토 없이 바로 고친다. 제안은 작업 재개, 범위 확대, 중단된 실행의 재시작을 승인하지 않는다.

## 4. 채택과 최초 작성

1. `ALIGNS.md`는 프로젝트 루트에 둔다(workflow.md §10 「루트에 두는 파일」). 공개 저장소일 수 있으므로 비밀·개인정보는 적지 않는다. 여러 프로젝트에 공통인 개인 기준은 공유 저장소에 두지 않는다.
2. `ALIGNS.md`가 없으면 채택 직후 첫 정식 Task(없으면 다음 정식 Task)의 절차 5에서 작업지시자와 기준을 합의한다. 초안은 수행계획서에 쓰고, 작업지시자가 확인한 뒤에 `ALIGNS.md`로 저장한다.
3. 최소 절: 목적(Purpose) · 범위(Scope) · 성공 기준(Success Criteria) · 운영 원칙(Operating Principles) · 마지막 전체 확인 시각(`Last aligned`). 절 이름과 본문의 언어는 프로젝트 문서 언어를 따른다.
4. `{AGENT_INSTRUCTIONS_FILE}`에 연결 문장을 넣는다. 최소 문장: 「작업을 시작할 때 `ALIGNS.md`를 읽고, 그 기준을 범위·중요한 결정·결과 검토에 적용한다. 기준의 변경은 작업지시자의 확인을 받은 경우에만 반영한다.」 `align` 스킬을 설치한 프로젝트는 스킬이 제공하는 연결 블록을 대신 써도 된다.
