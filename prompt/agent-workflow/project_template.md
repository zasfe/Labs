# 프로젝트 적용 문서 양식

이 파일은 playbook을 채택한 프로젝트가 **자기 적용 문서로 복사해 채우는 양식**이다. 적용 문서는 playbook 폴더 밖에 둔다([README](README.md) 채택 절차). 원본 양식은 playbook 안에 그대로 두고 값 열을 비워 둔다 — 값은 프로젝트의 적용 문서에만 적는다. 아직 정할 수 없는 값은 빈 칸이 아니라 `미정 — <확정할 Task·절차>`로 적고(README 「아직 정할 수 없는 값」), 확정되면 갱신한다.

## 머리 기록란

적용 문서에서 이 파일의 우선순위는 **적용 문서 > playbook**이다(프로젝트 예외 절).

| 항목 | 값 |
|---|---|
| 복사한 playbook 버전 | |
| playbook 정본 위치(받은 출처) | |
| 적용 문서 위치(playbook 폴더 밖) | |
| 제안 접수 창구(교훈 제안을 보내는 방법 — 정본 보유 쪽이 정함) | |

## 바인딩 표

playbook의 `{자리_이름}`에 프로젝트 값을 채우는 표. 각 행의 의미 열은 playbook이 정하고, 값 열은 프로젝트가 채운다. 적용 문서로 복사할 때 표 바로 앞의 바인딩 표식 주석 줄을 그대로 유지하고, 행의 첫 칸에는 `{자리_이름}`을 적는다(의미 열은 적용 문서에서 생략해도 된다 — 열 구성은 `| 자리 이름 | 의미 | 값 |` 또는 `| 자리 이름 | 값 |`). 무참조 게이트는 이 표에서 첫 칸의 자리 이름을 읽는다. 쓰지 않는 자리는 값 칸에 「없음」과 사유를 적는다. 의미문에 「(선택)」이 붙은 자리는 workflow가 선택 문서로 정한 것이다. 게이트 자리(`..._GATE`)는 게이트를 둔다면 그 명령을 적고, 두지 않으면 「없음」과 사유를 적는다.

## 주요 변경 목록

`{MAJOR_CHANGE_LIST}`의 실제 내용을 적는 절. 위임 승인 아래에서도 조정 세션이 중지하고 `{HUMAN_ROLE}`에게 질문해야 하는 변경을 이 프로젝트의 언어로 나열한다(예: 설계 결정 변경, 정본 문서 변경, 외부 계약 변경). 각 항목에 어디를 보면 해당 변경인지 판별할 수 있는지를 함께 적는다.

## 근거 색인

playbook 체크리스트 항목의 고정 ID와 그 항목이 생긴 이 프로젝트의 원 사례를 잇는 표. playbook에는 원 사례의 번호·이름을 쓰지 않으므로, 원 사례의 출처는 이 표에만 남긴다. 규칙 문구가 바뀌어도 ID로 연결이 유지된다.

## 결정 원장 행 형식

`{DECISION_LEDGER}`의 한 행은 최소 다음 열을 가진다. 결정을 뒤집으면 옛 행의 상태를 `대체됨 → ` + 새 번호로 바꾼다. 문서 끝에는 당면 과제 절을 두고 Task 종료 때 갱신한다.

| 번호 | 결정 | 출처 | 상태 |
|---|---|---|---|
| `{DECISION_ID_FORMAT}` 형식의 번호 | 정한 내용 한두 문장 | 결정을 정한 문서(수행계획서·승인요약서 등) | 유효 · 대체됨 → 새 번호 |

## 결정 원장 대조 표

수행계획서에 쓰는 대조 표. 이번 변경과 관련 있는 원장 행을 한 줄씩 적는다.

| 원장 번호 | 관련 여부 | 이번 변경과의 관계 |
|---|---|---|
| | | |

계획서·보고서를 보관 폴더로 옮기는 시점은 프로젝트가 정한다. 규칙 ID를 폐기하면 playbook의 CHANGELOG에 「폐기: ID — 이유」로 적는다.

## 로드맵 최소 절

`{ROADMAP_FILE}`가 갖출 최소 형식. 형식은 첫 Task 등재 때 확정해 `{ROADMAP_ENTRY_FORMAT}`에 적고 이후 바꾸지 않는다(그 전까지 값 칸은 `미정 — 첫 Task 등재 때 확정`).

- 제목 형식: Task마다 한 절, 제목 한 줄. 최소 예 `### <Task ID> — <제목> <상태> (<날짜>)`. 같은 Task 제목은 문서 전체에 정확히 1건이다(`{TASK_CI_CMD}`의 최소 검사가 이를 본다).
- 절 본문: 범위(무엇을 하고 무엇을 하지 않는가) · 의존(먼저 끝나야 하는 Task) · 결과(끝난 뒤의 상태와 근거 보고서 위치).
- 상태 어휘: 프로젝트가 몇 개로 정해 적용 문서에 적는다. 예: 예정 · 진행 · 완료 · 취소.
- 날짜의 의미: 한 가지로 고정해 적는다. 예: 완료 승인일(예정 Task는 등재일).

## 오늘할일 최소 절

`{ORDERS_FILE}`가 갖출 최소 형식. 절차 1·2([workflow.md](workflow.md) §5)가 요청을 확보해 여기에 기록한다.

- Task 줄 형식: Task마다 한 줄 이상. 최소 예 `- [<상태>] <Task ID> — <제목>`.
- 상태: 프로젝트가 정한 어휘를 쓴다. 예: 요청 · 진행 · 차단 · 완료.
- 여러 날에 걸친 Task: 그날 파일에 이어 적고 착수 파일을 가리킨다. 이전 날 항목은 한 줄로 줄여도 된다.
- 재개 절차: README 현황 블록 순서를 따른다(오늘할일 → 로드맵 → 현재 단계 계획서 → 직전 Stage Summary). 미해결 항목은 절차 12에서 적는다.
- 사후 기록 위치: 후보 CI 전 마지막 커밋에는 완료 판정을 적을 위치만 적고, CI·반영 결과와 완료 판정은 `{POSTMERGE_RECORD}`에 적는다.
