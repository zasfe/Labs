# Go 구현 지침

Go로 구현하는 프로젝트에만 추가되는 규칙과 함정을 담는다. [workflow.md](workflow.md)를 전제로 한다 — 원리는 그쪽에 있고, 이 문서는 Go 고유의 사실·도구·표기만 쓴다. HTTP 요청 기반 CLI에만 해당하는 규칙은 [go_httpcli.md](go_httpcli.md)에 있다.

- `{자리_이름}`의 의미는 [project_template.md](project_template.md) 바인딩 표에 있고, 값은 그 양식을 복사해 채운 프로젝트 적용 문서에 있다. 용어(golden·sentinel 등)의 뜻은 [workflow.md](workflow.md)의 용어 표에 있다.
- 체크리스트 ID(`GO-nn`)는 재사용하지 않는다.

---

## 1. 툴체인과 실행 환경

- Go 툴체인을 격리된 실행 환경에서만 돌리고 호스트에는 설치하지 않는 프로젝트는, 모든 빌드·테스트·린트를 `{TEST_RUNNER}`로 실행한다 — 빌드 `{BUILD_CMD}` · 단위 테스트 `{UNIT_TEST_CMD}` · 린트 `{LINT_CMD}`.
- 테스트 실행 환경은 자격증명도 네트워크도 없는 격리 환경으로 둔다. 네트워크가 필요한 도구 실행은 `{NET_RUNNER}`로 하되 테스트는 거기서 돌리지 않는다.

- [ ] **GO-01 툴체인 이미지와 버전을 정확히 고정했는가**
  툴체인을 컨테이너 이미지로 쓰는 프로젝트는 `{TOOLCHAIN_IMAGE}`처럼 **패치 버전까지 정확히 고정**한다. 릴리스 빌드가 `{TOOLCHAIN_VERSION}` 정확 일치를 강제하는 프로젝트에서 패치 버전이 움직이는 rolling 태그를 쓰면, 패치가 오르는 순간 빌드가 **조용히** 깨진다.

## 2. 죽은 코드와 중복 정리

- [ ] **GO-02 미사용 함수·플레이스홀더가 남아 있지 않은가 — 컴파일러가 잡아 주지 않는다**
  Go는 **미사용 import와 미사용 지역 변수는 컴파일 오류로 잡지만, 미사용 비공개(unexported) 함수·상수는 잡지 않고** `go vet`도 잡지 않는다. 게이트 `{DEADCODE_GATE}`를 두더라도 게이트 통과와 별개로 선언별 사용처를 센다(게이트가 죽은 상수를 놓치는 한계는 WA-09). 게이트가 도구를 내려받아야 하면 그 실행만 `{NET_RUNNER}`로 한다.
  원리·사례: [workflow.md](workflow.md) §6-1 WA-09 · WA-12
  <br>*사례 — 진입 함수를 지운 뒤 그것만 쓰던 보조 함수가 죽었고, 남은 import 때문에 빌드가 깨졌다.*

- [ ] **GO-03 중복을 정리하기 전에 "통합 대상"인지 "삭제 대상"인지 가렸는가 — 호출부를 센다**
  선언의 프로덕션 호출부가 0이면 통합이 아니라 삭제다. 삭제 뒤 `{BUILD_CMD}`가 rc=0이면 호출부가 없었다는 증명이 된다.
  원리·사례: [workflow.md](workflow.md) §6-1 WA-09

- [ ] **GO-04 "통합을 막는 차이"가 Go 타입 계약으로 정말 다른지 실측했는가**
  Go의 예: `json.Number`는 `String()`을 가진 Stringer이고 `fmt.Sprint`는 Stringer의 `String()`을 부르므로, 숫자 타입 분기를 따로 둔 두 변종도 같은 문자열을 낸다.
  원리·사례: [workflow.md](workflow.md) §6-1 WA-08

## 3. 테스트의 단정과 기대값

- [ ] **GO-05 기대값을 검증 대상 함수로 만들지 않았는가 — 개수를 명시한 리터럴로 적는다**
  폭이 긴 문자열은 `strings.Repeat(" ", 10)`처럼 **개수를 명시**하되 검증 대상 함수는 부르지 않는다.
  원리·사례: [workflow.md](workflow.md) §6-1 WA-07

- [ ] **GO-06 부분 일치 단정이 대체 경로의 출력까지 통과시키지 않는가**
  Go 테스트에서는 `strings.Contains` 같은 부분 문자열 포함 검사가 대표적이다. 처방은 원리 항목을 따른다.
  원리·사례: [workflow.md](workflow.md) §6-1 WA-18

- [ ] **GO-07 목록 출력형 검사기의 실패를 종료 코드로 만들었는가 — 위임 지시의 포맷 검사**
  `gofmt -l`은 위반 파일을 **출력만 하고 rc=0**이다. "출력 없음"을 검증으로 삼는 지시에는 `out=$(gofmt -l …) || exit 1; test -z "$out" || exit 1`처럼 위반이 곧 실패인 형태를 쓴다.
  원리·사례: [workflow.md](workflow.md) §4

- [ ] **GO-08 건너뛴 테스트(`t.Skip`)를 완료 증거로 읽지 않았는가**
  `t.Skip`으로 건너뛴 테스트와 단독 실행 테스트, 스텁 테스트는 완료 증거가 아니라 **블로커**다. 구현하거나 명시적으로 보고한다. 블로커 목록은 [workflow.md](workflow.md) §6 「완료 판정 시 블로커」를 본다.

## 4. 역검증(mutation)의 Go 함정

원리·사례는 [workflow.md](workflow.md) §6-1 WA-03·WA-14·WA-15·WA-19를 본다. 아래는 Go 컴파일러·테스트 도구 때문에 생기는 함정이다.

- [ ] **GO-09 변이가 import를 죽여 빌드를 깨뜨리지 않았는가**
  Go는 미사용 import를 컴파일 오류로 잡으므로 호출문을 지우는 변이가 가장 흔한 원인이다. 결함 값 표기 예: `0o600` → `0o644`, `if cond` → `if false && cond`.
  원리·사례: [workflow.md](workflow.md) §6-1 WA-14

- [ ] **GO-10 rc≠0인데 `--- FAIL`이 0건이면 빌드 오류부터 찾았는가**
  `go test` 출력의 `--- FAIL` 줄만 세면 빌드가 깨진 패키지는 한 줄도 내지 않는다. 출력의 `build failed`를 먼저 찾는다.
  원리·사례: [workflow.md](workflow.md) §6-1 WA-14

- [ ] **GO-11 침묵하는 변이는 `panic`을 심어 도달성부터 가렸는가**
  Go에서는 함수 본문 첫 줄에 `panic`을 심는다.
  원리·사례: [workflow.md](workflow.md) §6-1 WA-19

## 5. 커버리지 측정

목표 수치와 게이트는 `{COVERAGE_TARGETS}`·`{COVERAGE_GATE}`를 따른다.

- [ ] **GO-12 낮은 커버리지 여럿을 한 설명으로 묶지 않고 패키지별로 `-coverpkg`까지 따로 쟀는가**
  Go에서는 패키지마다 **자체 테스트만의 커버리지**와 `-coverpkg`로 **다른 패키지의 테스트가 덮어 주는 몫**을 나란히 잰다.
  원리·사례: [workflow.md](workflow.md) §6-1 WA-11 · WA-13

## 6. 계약 고정 자산

기존 계약을 고정하는 자산은 **코드를 자산에 맞춘다. 반대 방향은 금지**다.

- [ ] **GO-13 golden 파일·종료 코드 기준선을 재생성하지 않고, 바꿀 때는 의도된 계약 변경으로만 손 갱신했는가**
  golden 파일은 출력 형식 계약을 고정한다. 기준 구현이 있으면 그 구현과의 출력 동등성도 고정한다. 종료 코드 기준선(`{SMOKE_CONTRACT}`)과 릴리스 빌드가 요구하는 `{TOOLCHAIN_VERSION}` 정확 일치도 같은 자산이다. golden 개수는 보고서의 값을 믿지 않고 `{GOLDEN_COUNT_CMD}`로 실측해 확인한다. 아래 표는 golden·호환 기준선(GO-14)에 함께 적용한다.

  | | 최초 작성 | 의도된 계약 변경 | 깨졌을 때 |
  |---|---|---|---|
  | 기준 구현 있음(호환 대상이 있는 프로젝트) | 구현과 함께 만들고 내용을 사람이 검토한다 | 승인된 계획에 명시하고 **손으로** 갱신해 diff를 검토한다. 생성 도구 일괄 재생성·덤프 훅은 금지 | 구현이 계약에서 벗어났다는 신호다. 자산이 아니라 코드를 고친다 |
  | 기준 구현 없음 | 구현과 함께 만들고 내용을 사람이 검토한다 | 승인된 계획에 명시하고 손으로 갱신해 diff를 검토한다. 일괄 재생성은 하지 않는다 | 승인된 계획에 없는 변경이면 코드를 자산에 맞춘다 |

- [ ] **GO-14 호환 기준선을 손 편집으로만 갱신했는가 — 실패 메시지로 맞춘다**
  호환 기준선(기존 관측 동작 — 도움말·명령 트리 등 — 을 고정한 기준 파일)은 기준 구현이 있는 프로젝트에서 **재생성하지 않는다.** 의도된 계약 변경을 반영할 때만 **손으로** 고치며, 맞추는 기준은 호환 기준선 테스트의 **실패 메시지(첫 불일치 줄)** 다. 덤프 훅·임시 출력 코드는 쓰지 않는다. 기준 구현이 없어 기준선이 아직 없으면 최초 기준선은 구현과 함께 만들고 내용을 사람이 검토한다(위 표 「기준 구현 없음」).
  원리·사례: [workflow.md](workflow.md) §4 「허용되는 방법을 지시에 적는다」

## 8. 디렉터리 관례와 루트 파일

- 실행 진입점은 관례대로 `cmd/`에, 외부에 공개하지 않을 패키지는 `internal/`에 둔다(`internal/`은 컴파일러가 바깥 트리의 import를 막는다). 그 밖의 디렉터리를 포함한 프로젝트의 소스 경로는 `{SRC_DIRS}`로 기록한다. 최상위 폴더를 늘리지 않는 원칙은 [workflow.md](workflow.md) §10 「디렉터리 배치」를 본다.
- 모듈 정의 파일 `go.mod`는 Go 모듈 루트에서만 인식되므로 **루트에 둔다**([workflow.md](workflow.md) §10 「루트에 두는 파일」의 "언어 모듈 정의 파일"). 루트에 두는 근거와 의존성 정책은 프로젝트가 기록한다.
