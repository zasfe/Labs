# 컨테이너·WSL 실행 환경 지침

**선택 부록.** WSL2 위에서 docker compose로 빌드·테스트 환경을 격리해 쓰는 프로젝트만 채택한다. 그 밖의 환경에서는 이 문서를 복사 대상에서 빼도 다른 문서가 깨지지 않는다. [workflow.md](workflow.md)와 언어 문서([go.md](go.md))를 전제로 하며, 실 자격증명이 있는 프로젝트의 원칙은 [go_httpcli.md](go_httpcli.md)가 쓰고 이 문서는 compose·마운트 구체만 쓴다.

- `{자리_이름}`의 의미는 [project_template.md](project_template.md) 바인딩 표에 있고, 값은 그 양식을 복사해 채운 프로젝트 적용 문서에 있다.
- compose 서비스 이름·파일 이름·이미지 태그는 프로젝트마다 다르므로 「테스트 서비스」(`{TEST_RUNNER}`가 실행되는 곳)와 「개발 서비스」(`{NET_RUNNER}`가 실행되는 곳)로 쓴다.
- 체크리스트 ID(`EN-nn`)는 재사용하지 않는다.

## 1. 테스트 서비스와 개발 서비스

호스트에는 빌드 툴체인을 두지 않고 모든 빌드·테스트·린트를 컨테이너로만 실행하는 프로젝트의 규칙은 언어 문서(Go는 [go.md](go.md) §1)에 있다. 이 절은 그 컨테이너를 어떻게 둘로 나누는지를 쓴다.

- [ ] **EN-01 테스트 서비스를 비밀 파일·네트워크 없이 정의하고, 테스트를 거기서만 돌렸는가**
  서비스를 둘로 나눈다. 테스트 서비스는 compose 정의에 **환경 파일 지시를 두지 않고**, **네트워크를 끄고**(네트워크 없음 모드), 작업 트리의 실 비밀 파일 `{SECRET_FILE}`을 **빈 파일로 덮어 마운트**한다. 이러면 설정이 주입되지도, 나갈 길이 있지도 않으며, 현재 디렉터리 기준으로 비밀 파일을 읽는 경로가 생겨도 내용이 실패 메시지에 찍히지 않는다. 남는 것은 로컬 루프백 가짜 서버뿐이다. 개발 서비스는 환경 파일 지시로 실 자격증명이 주입되고 네트워크가 열려 있다.
  테스트·게이트·위임 지시서의 실행 명령은 `{TEST_RUNNER}`로 **명시**한다.
  원리·사례: [go_httpcli.md](go_httpcli.md) HC-01

- [ ] **EN-02 개발 서비스의 주입된 환경 변수가 비밀 파일보다 먼저 읽히는지 확인하고 탐침을 짰는가**
  개발 서비스의 비밀은 compose의 환경 파일 지시로 **프로세스 환경 변수**로 들어온다. 설정 로더가 프로세스 환경을 먼저 읽는 프로젝트(HC-02)에서는, 실행 때 대상 프로그램의 환경 파일 지정 옵션으로 가짜 파일을 줘도 실제 접속 대상이 읽힌다. 개발 서비스에 수동 탐침을 돌리기 전에 서비스 정의에 환경 파일 지시가 있는지 먼저 보고, 있으면 HC-02의 탐침 제한을 따른다.
  원리·사례: [go_httpcli.md](go_httpcli.md) HC-02

## 2. 마운트 파일시스템과 git 실행 권한

- [ ] **EN-03 새 실행 스크립트를 추가할 때 인덱스 실행 권한을 직접 줬는가**
  WSL2에서 윈도 드라이브를 9p 계열로 마운트하고 `metadata` 옵션이 없으면 모든 파일이 `0777`로 보이고 추적 파일 전체가 모드 변경으로 오검출되므로, 이런 저장소는 `core.fileMode=false`로 둔다. 그러면 git은 **새로 추가되는 파일의 실행 비트를 무시하고 `100644`로 기록한다.** 작업 트리에서 `chmod +x`를 해도 인덱스는 바뀌지 않는다. 로컬에서는 파일이 항상 `0777`이라 끝까지 드러나지 않다가, 새로 clone한 곳(릴리스 빌드·다른 머신)에서 exit 126으로 죽는다.

  ```bash
  git update-index --chmod=+x <새 스크립트 경로>   # chmod +x 만으로는 부족하다
  ```

  `{SCRIPT_PERMS_GATE}`를 두는 프로젝트는 추적 중인 스크립트 전체의 인덱스 권한을 검사하게 하고, 전체 CI `{CI_CMD}`의 앞 단계에 둔다 — 빌드·테스트 뒤에 터지면 exit 126만 보이고 원인이 드러나지 않는다.
  <br>*사례 — 새 셸 스크립트를 추가하고 작업 트리에서만 실행 권한을 줬다 → 인덱스에는 일반 파일(`100644`)로 기록됐고 로컬은 모든 파일이 실행 가능으로 보여 드러나지 않았다 → 새 clone에서 스크립트가 exit 126으로 실패했다.*

## 3. compose 파일을 옮길 때

compose는 프로젝트 이름을 **compose 파일이 있는 디렉터리 이름**에서 가져온다. 루트 밖으로 옮기면 볼륨·네트워크 이름이 조용히 바뀐다. 루트에 두어야 하는 파일의 범위와 이유는 [workflow.md](workflow.md) §10 「루트에 두는 파일」을 따른다.

- [ ] **EN-04 옮긴 compose 파일의 최상단에 프로젝트 이름을 명시했는가**
  옮긴 뒤 `docker compose -f <옮긴 파일> config`가 출력하는 `name:`을 옮기기 전 값과 비교한다. 하위 디렉터리에 두는 compose 파일은 최상단에 `name:`을 **반드시 명시**한다.

  ```yaml
  name: <옮기기 전 config 출력의 name 값>
  services:
    ...
  ```

  <br>*사례 — 옮기려는 compose 파일에 `config`를 돌리자 프로젝트 이름이 하위 디렉터리 이름으로 나왔다. 이대로 옮기면 이름에서 파생되는 캐시 볼륨이 새로 만들어진다.*

- [ ] **EN-05 옮긴 compose 파일 안의 경로를 새 위치 기준 상대 경로로 다시 계산했는가**
  경로는 compose 파일 위치 기준이다. 빌드 컨텍스트·Dockerfile 경로·환경 파일 경로·바인드 마운트를 모두 다시 계산한다. 하나라도 옛 기준으로 남으면 빌드 대상이나 마운트·환경 파일이 다른 곳을 가리킨다.

## 4. 진단 실행의 흔적

- [ ] **EN-06 개념 증명·진단용 컨테이너 실행이 식별 가능한 흔적만 남기고 정리 가능한가**
  진단을 위해 임시로 이미지를 빌드하거나 컨테이너를 돌릴 때는 **흔적을 남기지 않는다.** 흔적이 남더라도 정리 규칙이 찾을 수 있도록 프로젝트가 정한 식별 표식을 붙인다. 표식은 작업 단위를 구별할 수 있어야 한다(예: 접두 + 작업 번호). 표식·라벨·접두와 정리 명령은 적용 문서에 적는다.
  1. 진단 Dockerfile의 **모든** `RUN` 명령에 표식을 넣는다 — 예 `RUN : <표식> && …`. 빌드 레코드는 이미지 유무와 무관하게 남고, 표식 없는 `RUN` 레코드가 하나라도 있으면 부모 체인째 남는다.
  2. 이미지가 필요 없으면 `docker build --output type=cacheonly`로 이미지를 만들지 않는다.
  3. 이미지가 필요하면 라벨을 붙이고 끝나면 `docker image rm`으로 지운다.
  4. 컨테이너는 `docker run --rm`으로 돌린다. 분리 실행은 같은 라벨을 붙이고 종료 때 `docker rm -f`로 지운다.
  5. 진단 전용 캐시 마운트 id에는 표식 접두를 붙인다.
  6. 정리 단계를 두는 프로젝트는 안전망으로 전체 CI `{CI_CMD}`가 성공하면 라벨·접두·`RUN` 표식이 붙은 항목(빌드 레코드 포함)만 지운다. 라벨 없는 dangling 이미지는 대상이 아니다.
