# 작업 절차

> **이것은 바이브 코딩이 아니다.** AI 출력을 읽지도 않고 수락하는 게 아니다.
> 모든 계획은 검토되고, 모든 결과물은 검증되며, 모든 결정 뒤에는 사람이 있다.
> AI는 절차를 따르는 도구가 아니라 판단을 수행하는 협업자다. 다만 모든 최종 의사결정과 품질 책임은 작업지시자에게 있다.

거시적 워터폴(계획 → 승인 → 구현 → 검증) + 미시적 애자일(단계별 반복)을 AI가 동시에 수행한다.

이 문서는 이 playbook을 채택한 프로젝트의 **영구 규범**이다. 새 세션은 이 문서를 읽고 즉시 절차를 따를 수 있어야 한다.

- `{자리_이름}`의 의미는 [project_template.md](project_template.md) 바인딩 표에 있고, 값은 그 양식을 복사해 채운 프로젝트 적용 문서에 있다.
- 사람 역할은 「작업지시자」로 쓴다. 프로젝트가 다른 이름을 쓰면 `{HUMAN_ROLE}` 값으로 바꿔 읽는다.

### 용어

이 문서에서 쓰는 뜻만 적는다. **세션을 끊는 단위는 절차 n의 단계**(§5 표의 한 행)이며, 한 절차 안에서 Stage 여러 개를 수행할 수 있다.

| 용어 | 이 문서에서의 뜻 |
|---|---|
| 절차 n | §5 표의 n번 행(1~13). 「단계」는 절차 n의 단계를 가리키고 Stage와 다르다 |
| Stage | 절차 7에서 구현을 나눈 승인 단위. 완료보고서를 모아 Stage Summary 한 편으로 승인받는다(`2a`·`2b`처럼 쪼갤 수 있다) |
| 작업 단위 | 한 Task를 나눈 업무 단위(Work Item). 담당자 하나가 자기 범위의 계획·구현·검증·문서를 맡는다(§4) |
| 조정 세션 | 주 작업자의 세션. 위임·재현·승인 지점 관리를 맡고 보조 에이전트에 일을 맡긴다 |
| 단계 책임자 | 절차 9에서 완료보고서를 검토해 Stage Summary를 쓰는 사람 또는 세션. 완료보고서를 쓰는 담당자(절차 8)와 구별한다 |
| 구현 위임자 | 조정 세션이 구현을 맡긴 보조 에이전트. 실행 한도(`{AGENT_TURN_LIMIT}`)가 있다 |
| 보조 에이전트 | 조정 세션이 조사·검토·구현을 맡긴 별도 에이전트(구현 위임자 포함) |
| 정식 Task | §5의 절차 1~13을 따르는 Task. 축약해도 되는 범위는 §5 「절차를 축약할 때」가 정한다 |
| 독립 검토 | 작성자가 아닌 검토자(사람 또는 별도 에이전트)의 검토. 결과는 해당 Stage Summary에 기록한다 |
| rc | 명령의 종료 코드(return code). 0이 성공이다 |
| SKIP | 게이트가 전제 부재 등으로 검사를 건너뛴 결과. rc가 0이어도 검사를 통과했다는 뜻이 아니다 |
| fail-closed | 판정 불가·검사 실패를 통과로 처리하지 않고 실패로 처리하는 방식 |
| sentinel | 고정된 문구·값으로 정의해 호출자가 같은 값으로 식별하는 오류. 원문을 감싸 담지 않는다 |
| golden | 출력 형식 계약을 고정해 두고 비교하는 기준 출력 파일. 기준 구현이 있으면 그 구현과의 출력 동등성도 고정한다 |
| 기준 구현 | 새 구현이 호환해야 하는 기존 구현. 있는 프로젝트에만 해당한다 |
| 핵심 계층 | 입력 검증·판정 규칙을 소유하는 계층. 진입점은 이 계층을 거친다 |
| 진입점 | 같은 기능으로 들어오는 길. 명령행과, 프로젝트에 있는 다른 어댑터(서버·다른 프로토콜 등) |
| 격리 병합 후보 | 정식 Task의 후보 CI를 돌리려고 만든 임시 작업 사본(§5 「완료 선언 전 전수 확인」·§10 병합 정책) |
| 역검증 | 변이 시험(mutation). 수정을 결함 상태로 되돌리거나 변이를 넣어 테스트가 실제로 실패하는지 본다(WA-03) |
| RED | 테스트가 수정 전 코드에서 실패하는 상태 |
| pp | 퍼센트포인트. 커버리지 수치 변화량의 단위 |

## 2. AI의 자율 판단 원칙

AI에게 구현 절차를 모두 지시하지 않는다.
테스트 범위, 구현 방식, 적절한 모델·실행 수단(보조 에이전트 포함)의 선택은 **AI가 스스로 판단**한다.

단, 다음은 **항상 작업지시자가 판단**한다.
- 설계 방향
- 요구사항 변경
- 품질 승인

### 구현 필요성 검토 (구현 착수 전 필수, 순서대로)

1. 구현하지 않고 해결 가능한가
2. 기존 코드·설정·패턴을 재사용할 수 있는가
3. 표준 라이브러리로 해결 가능한가
4. 플랫폼 기본 기능으로 해결 가능한가
5. 이미 사용 중인 의존성으로 해결 가능한가
6. 설정 변경·삭제·최소 변경으로 해결 가능한가
7. 위 방법으로 해결할 수 없는 경우에만 **최소 코드**를 작성한다

## 3. 디버깅 원칙

**버그 보고는 증상으로 간주한다.**

- 수정 전에 재현, 실행 흐름, 관련 호출 경로를 확인하고 **근본원인**을 찾는다
- 동일한 원인을 공유하는 공통 지점이 있다면 **해당 위치를 수정**한다
- 호출자마다 동일한 수정을 반복하는 것은 가능한 한 피한다

## 4. 병렬 작업 원칙

하나의 Task는 여러 **작업 단위(Work Item)** 로 분리하여 병렬 수행할 수 있다.

- 각 작업 단위는 하나 이상의 AI 또는 보조 에이전트가 담당
- 담당 AI는 **자신의 작업 범위에 대해서만** 계획, 구현, 검증, 문서를 작성
- 작업지시자는 개별 작업 단위의 모든 보고서를 검토하지 않는다. **단계 승인요약서(Stage Summary)** 를 기준으로 승인 여부를 판단한다
- 필요한 경우에만 단계별 완료보고서를 추가로 확인한다

### 보조 에이전트에 위임할 때 — 응답을 확인하고 진행한다

조사·검토를 보조 에이전트에 맡겼으면 **그 응답을 받은 뒤에** 다음 단계로 넘어간다.
특히 **되돌리기 어려운 단계**는 응답 전에 하지 않는다.

| 응답 전에 해도 되는 것 | 응답 전에 하지 않는 것 |
|---|---|
| 조사 계속 · 계획서 초안 · 로컬 커밋 | **푸시 · PR 생성 · 병합** |

- 응답이 늦으면 **기다린다.** 에이전트가 비활성으로 표시돼도 결과가 나중에 올 수 있다 —
  비활성 표시는 "끝났다"가 아니라 "지금 실행 중이 아니다"일 뿐이다
- 기다릴 수 없는 사정이면 **작업지시자에게 상황을 보고하고 지시를 받는다.**
  AI가 스스로 "검토 실패"로 단정하고 진행하지 않는다
- **받지 못한 결과는 추측해서 쓰지 않는다.** 판정을 지어내는 것은 검토를 건너뛴
  것보다 나쁘다
- 승인을 받아 먼저 나아갈 때는 **나중에 도착할 결과를 반영할 자리를 남긴다**

*사례 — 승인 지점 검토를 보조 에이전트 2개에 맡겼으나 둘 다 비활성 표시가 된 채 결과가 오지 않았다. 같은 위임 세션에 후속 지시를 2회 보내도 응답이 없어 "검토 실패"로 판단하고 직접 대조로 전환해 구현·PR·병합까지 마쳤다 → 병합 직후 두 결과가 도착했고 판정은 "수정 필요"(지적 9건)였다 → 구현은 올바랐으나 문서 기재 3건이 틀려 정정 작업을 따로 만들어야 했다.*

▎검토의 목적은 **승인 전에 방향을 고치는 것**이다. 병합 뒤에 오면 그 목적이
사라지고 **사후 정정 Task가 하나 더 생길 뿐**이다.

**구현 위임자의 "확인함"도 조정 세션이 다시 본다.** 보조 에이전트 보고의 검증 주장은
조정 세션(주 작업자)이 같은 명령으로 재현한 것만 믿는다. 특히 두 가지는 자주 틀린다.

- **"출력 없음" 류 검증은 위반이 곧 실패하도록 짠다** — 위반을 출력만 하고 종료 코드 0으로 끝나는
  검사 명령(목록 출력형 검사기)은 위반이 있어도 통과한다. 지시에는
  `out=$(검사 명령) || exit 1; test -z "$out" || exit 1`처럼 위반이 곧 실패인 형태를 쓴다
  (검사기의 종료 코드를 버리면 디스크에 없는 추적 파일·구문 오류도 통과한다)
- **값의 소비처가 둘 이상일 수 있는 판단은 전수 검색한다** — "이 키는 X로만 읽힌다"는 근거는
  키 이름을 `{SRC_DIRS}` 전체에서 검색해 확인한다

*사례 — 구현 위임자가 "포맷 검사 출력 없음"이라 보고했으나 위반이 1건 있었다(검사 명령이 위반에도 실패하지 않았다). 같은 단계에서 "이 설정 키는 환경 변수로만 읽혀 설정 파일 값이 무시된다"는 판단으로 키를 허용 목록에서 뺐으나, 다른 경로가 설정 파일에서 같은 키를 읽고 있었다 → 소비처를 전수 확인하지 않았다 → 기준 브랜치 대비 회귀였고 병합 전 독립 재검토가 잡았다.*

### 구현 위임 운영 — 실행 한도 · 동시 쓰기 · 규약 표기

구현 위임자는 **실행 한도(`{AGENT_TURN_LIMIT}`)** 가 있다. 한도에 닿으면 보고 없이 멈추고 미커밋 변경이 작업 트리에 남는다.

| 규칙 | 내용 |
|---|---|
| 처음부터 나눈다 | `{AGENT_TURN_LIMIT}`에 비해 대상이 많거나 파일이 많은 Stage(예: 7~8건 이상)는 `2a`·`2b`처럼 나눠 맡긴다 · 지시에 "커밋 우선 · 한도가 부족하면 남은 일을 보고"를 넣는다 |
| 멈추면 이어서 | `git status`로 남은 변경을 확인하고 **같은 위임 세션에 후속 지시**를 보내 마무리시킨다(새 에이전트는 맥락을 잃는다) |
| 같은 브랜치 동시 쓰기 금지 | 같은 브랜치에 커밋하는 구현 위임자를 동시에 띄우지 않는다 · 조정 세션도 그동안 커밋하지 않는다 · 읽기 전용 검토는 병행 가능 |
| `git add`는 경로 지정 | `-A` 금지 — 다른 작업의 변경을 쓸어 담는다 |
| 허용되는 방법을 지시에 적는다 | 금지만 적으면 위반이 반복됐다 — 지시에 **금지와 함께 허용되는 방법**을 적는다. 예: 손으로만 고치는 기준선 파일이면 "임시 출력 코드 금지"에 더해 "테스트 실패 메시지의 첫 불일치 줄로 맞춘다"까지 적는다(금지만 적었더니 같은 위반이 2회 반복된 사례가 있다) |
| 규약 표기는 지우지 않는다 | `{SIMPLIFICATION_MARKER}` 주석은 구현 위임자 정의(`{AGENT_DEF}`)가 정한 "의도적 단순화의 알려진 한계" 표시다. 저장소에 선례가 없다고 출처 불명으로 판단하지 않는다. 낯선 표기는 지우기 전에 에이전트 정의를 먼저 본다 |

*사례 — 저장소에 선례가 없는 낯선 단순화 표기를 출처 불명으로 판단해 지웠다 → 에이전트 정의를 확인하지 않았다 → 정의된 규약이었음이 드러나 복원해야 했다.*

### 작업단위 이름 규칙

구현 기술이 아니라 **사람이 이해할 수 있는 업무 단위**로 작성한다.

| 좋은 예 | 지양 |
|---|---|
| `backend`, `frontend`, `infra`, `docs`, `test` | `worker1`, `api2`, `temp`, `fix`, `misc` |

## 5. Task 진행 절차

모든 정식 Task는 아래 절차를 따른다. **절차를 건너뛰지 않는다.**
각 절차는 **독립 세션**으로 수행하는 것이 기본 원칙이며, 필요한 문서만 읽어 컨텍스트를 이어간다.

| # | 절차 | 산출물 |
|---|------|--------|
| 1 | 로컬 고유 Task 번호(`{TASK_ID_FORMAT}`)와 작업 요청 확보(요청 자체를 얻는다). 외부 이슈 트래커(`{ISSUE_TRACKER}`)는 선택적 참조 | 작업 요청 · 선택적 이슈 |
| 2 | 확보한 요청을 오늘할일에 기록. 여러 날에 걸친 Task는 그날 파일에 이어 적고 착수 파일을 가리킨다 | `{ORDERS_FILE}` |
| 3 | Task 브랜치 생성 | `{BRANCH_PATTERN}` |
| 4 | 관련 코드·문서·설정과 실제 실행 흐름 조사 · 루트 `ALIGNS.md`에서 이번 Task에 해당하는 기준 확인([alignment.md](alignment.md)) | — |
| 5 | **수행계획서** 작성(「작업 결과 기준」 절 포함 — [alignment.md](alignment.md) §2) → **[작업지시자 승인]** | `{PLAN_FILE}` |
| 6 | **구현계획서** 작성 (최소 변경 원칙) → **[작업지시자 승인]** | `{IMPL_PLAN_FILE}` |
| 7 | 작업 단위 정의 후 필요 시 병렬 수행 | — |
| 8 | 각 담당자가 작업 결과 기록 | `{STAGE_REPORT_FILE}` |
| 9 | 단계 책임자가 완료보고서를 검토해 요약 작성 — **§6-1 A·B·C** | `{STAGE_SUMMARY_FILE}` |
| 10 | 작업지시자가 **Stage Summary 기준으로 승인** 결정 | — |
| 11 | 모든 단계 완료 후 **최종 결과보고서**(「기준 대조」 포함) → **[작업지시자 승인]** — **§6-1 D** | `{REPORT_FILE}` · `{REPORT_HTML_POLICY}`에 따른 HTML |

### 절차 12의 로드맵 등재

`{ROADMAP_FILE}`은 `{ENTRY_DOC}`의 읽기 순서에 넣는다. 읽기 순서는 [README.md](README.md)의 표준 순서를 따른다. 새 세션은 이 문서로
현황을 파악하므로, 끝난 Task가 여기 없으면 **현황을 오독한다.**

기존 절 형식(첫 등재 때 정해 바인딩한 형식, `{ROADMAP_ENTRY_FORMAT}`)을 그대로 따르고 **새 형식을 만들지 않는다.**

*사례 — 끝난 Task 여섯 개가 로드맵에 등재되지 않은 채 쌓였다 → 로드맵이 오래전 Task에서 멈춰 그것이 최신으로 읽혔고, 실제로 수행·완료된 Task가 "제안" 상태로 남은 경우도 있었다 → 절차 12가 오늘할일만 가리키고 로드맵을 가리키지 않아 갱신을 강제하는 지점이 없었던 것이 원인이다.*

### 절차를 축약할 때 — 도달 경로는 축약하지 않는다

작은 Task에서 13단계를 전부 밟는 것이 과할 때가 있다. **축약 자체는 금지가
아니다.** 금지되는 것은 **어디까지 줄였는지 모른 채 줄어드는 것**이다.

| 구분 | 절차 | 근거 |
|---|---|---|
| **축약 불가** | 1(로컬 작업 요청) · 2(오늘할일 기록) · 3(브랜치) · **11(결과보고서)** · **12(로드맵·오늘할일 갱신)** · **13(판단 기록)** | 이것들이 **다음 세션에 도달하는 경로**다. 끊기면 §6-1 머리말대로 *기록이 존재하지 않는 것과 같다* |
| 규모에 따라 축약 가능 | 5·6(계획서) · 8·9(Stage 문서) | 그 Task **내부의 진행 문서**다. 다만 **승인은 축약하지 않는다** — 계획서를 줄이면 그만큼 대화로 승인을 받는다 |

- 축약했으면 **축약했다고 `{ORDERS_FILE}`에 적는다.** "절차 1~13 완료"는 전부 밟았을 때만 쓴다
- 13은 *"승격 없음"* 이라도 **판단을 적는 것**이 수행이다(실측 사례에서 판단 자체가 빠져 있었다)

*사례 — 1커밋짜리 문서 Task가 절차 11·12를 건너뛴 채 병합됐다 → 종료 사실이 외부 이슈 트래커에만 있고 저장소 문서 어디에도 없어 로드맵이 직전 Task에서 멈춘 채로 남았다 → 조사해 보니 그보다 앞선 Task들에서 이미 축소가 진행 중이었다(HTML 보고서는 이 Task까지 5건, 확인용 퀴즈는 앞선 4건이 빠졌고 두 집합이 일치했다). 그중 일부는 그 상태로 "절차 1~13 완료"를 선언했다.*

▎**축약이 판단이 아니라 표류로 일어났다.** 한 번 시작되면 어디서 멈추는지가
정해져 있지 않다 — 처음에는 부가 산출물이, 다음에는 계획서가, 그다음에는
보고서와 로드맵까지 빠졌다. 그래서 처방을 "성실히 하라"가 아니라
**줄여도 되는 것과 안 되는 것의 목록**으로 적는다.

#### 완료 선언 전 전수 확인

완료 판정을 적기 전에 **명령으로 확인한다.** 체크리스트와 달리 명령은 답을 낸다.

정식 Task는 결과보고·로드맵을 반영해 커밋한 뒤 **격리 병합 후보**(후보 CI를 돌리려고 만든 임시 작업 사본 — §10 병합 정책)에서 실행한다.
후보 CI 전 마지막 커밋의 `{ORDERS_FILE}`에는 **완료 판정을 적을 위치**(사후 기록)만 적는다. CI·반영 결과와 완료 판정은 커밋하지 않는 `{POSTMERGE_RECORD}`에 적고, 다음 정식 Task의 절차 4에서 정본에 반영한다(§10 병합 정책). 절차 12는 후보 CI 전에 끝낸다.
오늘할일 파일은 실제 파일로 지정한다. 보조 게이트의 생략(SKIP) 결과나
파일 존재만으로는 내용·정확한 번호를 확인할 수 없다.

```bash
N=<Task 번호>  # 실제 Task 번호로 교체
ORDERS_FILE=...  # 실제 오늘할일 파일로 교체
{TASK_CI_CMD}   # Task 번호 N을 바인딩이 정한 방식으로 넘긴다
grep -nE "<접두 표기>$N([^0-9]|$)" "$ORDERS_FILE"   # <접두 표기>는 {TASK_ID_FORMAT}의 접두(예: "Task ")
```

`{TASK_CI_CMD}`는 보고서 본문·`{REPORT_HTML_POLICY}`에 따른 HTML·정확한 로드맵 제목을 검증한 뒤 `{CI_CMD}` 전체를
수행하는 명령으로 바인딩한다. 이 기능이 없으면 빠진 검사를 사람이 수동으로 확인해 기록한다.
오늘할일 파일의 내용과 승인·의미는 사람이 별도 확인한다.

### A. 모든 [승인] 지점 공통

- [ ] **WA-01 계획과 달라진 것을 전부 적었는가**
  구현 중에 계획서가 예상하지 못한 제약이 드러나는 것은 정상이다. 문제는 조용히
  다르게 만드는 것이다. 달라진 항목·이유·결과적으로 나아졌는지를 승인요약서에 적는다.
  <br>*사례 — 테스트 배치가 순환 참조 때문에 계획서와 달라졌고, 외부에 공개하는 항목 3건이 계획 없이 추가됐다.*

- [ ] **WA-02 이번에 새로 쓴 코드에 테스트가 있는가**
  커버리지 총합이 기준을 넘는 것과 신규 로직이 덮이는 것은 다르다. **총합은 기존 코드가
  올려준다.** 이번 단계에서 추가한 함수를 하나씩 짚는다.
  <br>*사례 — 커버리지가 기준에 0.5% 미달이었는데, 원인을 보니 이번 Task의 신규 로직인 옵션 값 검증에 테스트가 하나도 없었다. 수치보다 이쪽이 문제였다.*

- [ ] **WA-03 그 테스트가 그 결함을 잡는지 확인했는가 — 역검증**
  **통과하는 테스트는 그 자체로 아무것도 증명하지 않는다.** 대상을 실제로 검사하지
  않는 테스트도 통과한다. 수정을 **결함 상태로 되돌려 그 테스트가 실패하는지** 본다.
  실패하지 않으면 그 테스트는 회귀를 막지 못한다. 확인 후 반드시 복원하고
  `git diff`가 비어 있는지 본다.
  <br>▎**동작이 같아야 하는 변경**(중복 통합·리팩터링)에서 특히 그렇다 — 그런
  변경은 테스트가 침묵해야 정상이므로, 침묵이 "지켰다"인지 "안 보고 있다"인지
  구별되지 않는다.
  <br>▎**역검증은 커밋한 뒤에 한다.** 되돌리는 수단은 보통 `git checkout -- <경로>`이고,
  그 명령은 **인덱스/HEAD 기준으로 복원**하므로 **아직 커밋하지 않은 편집을 함께 지운다.**
  Stage 구현을 마쳤으면 **측정 전에 커밋**한다 — 그래야 복원이 "결함 제거"이지
  "작업 삭제"가 되지 않는다. 복원 뒤 `git diff --quiet`로 트리가 깨끗한지 본다. 깨끗하지
  않으면 복원이 실패한 것이고, **깨끗한데 내 변경까지 사라졌다면** 커밋을 건너뛴 것이다.
  <br>*사례 — 죽은 상수 정리 Stage를 커밋하기 전에 대조 측정을 돌렸고, 경로 복원 명령이 **그 편집을 되돌렸다.** 같은 파일을 다시 고치고 커밋한 뒤 재측정했다 — 결과는 같았지만 측정 한 벌을 버렸다. 앞선 Task가 보고서에 적어 둔 실천("Stage를 먼저 커밋한다")이 체크리스트에는 없어 반복됐다.*
  <br>▎⚠ **아직 커밋되지 않은 새 파일은 `git checkout`으로 복원되지 않는다.**
  `error: pathspec … did not match any file(s) known to git`가 뜨고 **mutation이
  파일에 그대로 남는다.** 이 메시지는 역검증이 성공했다는 출력에 섞여 흘러가기
  쉽다. 새 파일을 만드는 Task는 ⓐ 역검증 전에 먼저 커밋해 두거나
  ⓑ 복원 후 `git status`와 **마커 문자열 grep**으로 잔존 0건을 확인한다 —
  `git diff`만으로는 untracked 파일의 오염을 볼 수 없다.
  <br>*사례 — 신설한 테스트 파일 4개에 mutation을 넣고 `git checkout`으로 되돌리려 했으나 전부 untracked라 실패했고, 네 파일 모두 무력화된 채로 남았다. 마커 문자열 grep으로 발견해 수동 복원했다.*
  <br>▎**결함 없는 사본(대조군)은 rc만이 아니라 건수·출력까지 본다.** 게이트나 검사
  도구를 역검증할 때 결함 사본이 실패하는 것만으로는 부족하다 — **대조군이 기대한 만큼 셌는가**를
  봐야 한다. 과대 집계는 실패가 아니라서 rc로는 드러나지 않는다.
  <br>*사례 — 문서 참조 검사 게이트의 대조군이 rc=0으로 통과했지만 근거 5건을 **17건**으로 셌다. 따옴표 없는 변수 전개가 와일드카드를 실제 파일 12개로 확장해 "`*`는 건너뛴다"는 규칙이 무력했다. 건수를 봤기에 잡혔다(와일드카드 전개를 꺼서 수정).*
  <br>*사례 — 파일 형식 판정을 되돌리자 텍스트 출력을 표 형식 파일로 저장하는 테스트가 저장된 바이트로 실패해, 이전 결함 동작이 정확히 재현됐다. 거부 로직·경고 출력을 각각 제거한 2건도 해당 테스트만 실패했다. 이 확인이 없으면 "테스트를 썼다"와 "그 테스트가 무언가를 지킨다"를 구분할 수 없다.*
  <br>▎**mutation 뒤 결함 상태가 실제로 만들어졌는지 대상 쪽에서 확인한다.**
  치환이 적용됐어도(`git diff`에 보여도) 같은 정보가 다른 자리에 남아 있으면
  결함 상태가 아니다. 그때의 통과는 "도구가 못 잡는다"도 "지킨다"도 증명하지 않는다 —
  검사 도구가 **무엇을 읽는지**(추출 범위)를 보고 그 전부를 결함 상태로 만든다.
  <br>*사례 — 문자열 치환이 적용되지 않았는데 rc=0이었다(`git diff` 빈 출력으로 발견). 다른 Task에서는 문서의 플래그 표에서 한 행을 지웠는데 문서-코드 대조 검사가 rc=0이었다. 치환은 적용됐으나 검사 도구가 **파일 안 모든 표 행**을 읽어 같은 절의 다른 표에서 찾았다. 두 행을 모두 지우자 불일치로 잡혔다.*

- [ ] **WA-04 명령의 종료 코드를 볼 때 파이프라인을 거치지 않았는가**
  `cmd | tail -4 ; echo $?`는 **`tail`의 종료 코드**다. 게이트와 계약을 종료 코드로
  판정하는 프로젝트(`{SMOKE_CONTRACT}`의 종료 코드 약속 · 게이트 종료 코드 · 사용법 오류 종료 코드)에서
  파이프라인을 거친 값을 읽으면 **통과를 실패로, 실패를 통과로** 본다.
  ```bash
  cmd > out.txt 2>&1 ; echo $?       # 이렇게 본다
  cmd | tail ; echo $?               # tail 의 코드다
  ```
  <br>*사례 — 두 번 오독했다. ① 한 하위 명령의 가드를 `rc=0`으로 읽고 "사용법 오류인데 0이다"라며 **계약 위반으로 보고할 뻔했다**(실제 `rc=2`로 정상). ② 스모크 스크립트를 `rc=2`로 읽고 스모크 실패로 판단했다(실제 `rc=0`). 둘 다 `| tail`이 원인이었고, 다시 확인해 정정했다.*
  <br>▎**실패 쪽 오독이 더 위험하다** — 통과를 실패로 읽으면 없는 결함을 보고하고,
  그 보고가 다음 Task의 조사 범위가 된다.

- [ ] **WA-05 검증을 추가했다면 모든 진입점이 그 검증을 거치는가**
  같은 기능에 들어오는 길(진입점)이 둘 이상인 경우가 많다 — **명령행**과, 프로젝트에 있는 다른 어댑터(서버·다른 프로토콜 등)가
  부르는 **하위 계층**, 그리고 한 함수 안에서도 **단일 대상·다중 대상** 분기가 갈린다. 한 길에만 검증을
  넣으면 다른 길은 같은 입력으로 틀린 결과를 낸다. 검증은 **핵심 계층이 소유하고 모든 진입점이 같은
  함수를 부르게** 한다.
  ```bash
  grep -rn "<검증함수>(" {SRC_DIRS}
  # 테스트 파일은 빼고 센다. 진입점 수와 호출 수가 맞는가. 분기(단일/다중 대상)보다 앞에 있는가
  ```
  <br>*사례 — 세 번 반복됐다. ① 옵션 하나의 검증을 명령행 경로만 보고 끝냈고 다음 Task에서 구멍이 드러났다. ② 한 조회 명령에서 서비스 계층만 핵심 계층의 기간 검증을 부르고 **명령행은 안 불러**, 시작일만 준 입력이 서비스에서는 거부되고 명령행에서는 기간이 뒤집힌 채 조회됐다(실제 서버 대상 실행에서 rc=0). ③ 서비스 함수는 기간 검증이 **단일 대상 경로에만** 있어 다중 대상 검색이 잘못된 기간을 모든 대상에 그대로 보냈다.*
  <br>▎역검증으로 확인한다 — 검증 호출을 한 경로에서만 되돌렸을 때 **그 경로의 행만** 실패해야
  한다. 서비스 검증을 단일 대상 경로로만 되돌리자 다중 대상 행만 실패했다.

- [ ] **WA-06 검증을 다른 함수에 맡겼다면, 그 함수가 이름대로 검증하는가**
  *"값 검증은 X에 맡긴다"* 는 주석이나 설계는 X가 실제로 그것을 검사할 때만 성립한다. 이름이
  `Validate…`여도 일부만 보는 경우가 있다. 맡기기 전에 **맡긴 함수의 본문**을 읽고, 거부되어야 할
  입력을 실제로 넣어 본다.
  <br>*사례 — 한 명령행 옵션 처리부의 주석은 *"값 검증은 핵심 계층의 기간 검증 함수에 맡긴다 — 명령행이 날짜를 다시 파싱하면 핵심 계층과 거부 조건이 어긋난다"* 였다. 그러나 그 함수는 기존 옵션 하나만 검사했고 시작일·종료일 옵션은 형식도 순서도 보지 않았다. 실제 서버에서 시작일에 엉뚱한 문자열을 주자 **rc=0**이었고(관대한 파서가 0년 0월 0일로 읽어 전체 기간의 이력이 왔다), 뒤집힌 기간도 rc=0으로 조회됐다. **맡긴 쪽도 맡은 쪽도 검증하지 않는** 구조였다.*
  <br>▎*"옵션을 받아들이는 것과 효과를 내는 것은 다르다"* 와 같은 뿌리다 — 선언만 된 옵션,
  해석만 되고 적용되지 않은 옵션이 있었다. 이 항목은 그것을 **검증 함수**에 적용한 것이다.

- [ ] **WA-07 기대값을 검증 대상으로 계산하지 않았는가 — 자기참조 금지**
  `want := 대상함수("ID", 12) + …`처럼 **기대값을 검증 대상 자신으로 계산**하면,
  대상을 뒤집었을 때 기대값도 같이 뒤집혀 비교가 **항상 성립한다.** 대조는 하지만
  어떤 결함도 잡지 못한다. 기대값은 리터럴로 적는다 — 폭이 길면 반복 표현으로
  공백 10개처럼 **개수를 명시**하되 검증 대상은 부르지 않는다.
  <br>*사례 — 표 헤더를 대조하는 테스트 4곳이 기대값을 공통 패딩 함수로 계산했다. 그 함수의 좌우 반전 mutation이 함수 자신의 테스트만 깨고 호출부 3개 패키지는 조용히 통과했다. 리터럴로 바꾸자 3개 패키지가 모두 실패한다.*
  <br>▎**중복 통합 Task마다 다시 만난다.** helper를 옮기면 그 helper를 쓰던
  기대값도 함께 옮겨지기 때문이다. 새로 쓰는 테스트에서는 잘 생기지 않고,
  **기존 테스트를 새 API로 전환할 때** 생긴다.

- [ ] **WA-08 동일성 판정을 본문으로 했는가 — 시그니처를 해시에 넣지 않는다**
  함수 이름과 매개변수 이름은 의미가 아니다. 시그니처를 포함해 해시하면 **이름 차이가
  의미 차이로 오인된다.** 본문으로 후보를 묶은 뒤 시그니처를 눈으로 대조하는 2단계로 한다.
  <br>*사례 — 이름만 대소문자가 다른 두 함수가 서로 다른 변종으로 보였으나 본문은 바이트 동일이었고, 다른 헬퍼가 두 갈래로 갈린 것도 매개변수 이름 차이뿐이었다.*
  <br>▎**해시 값을 문서 간 대조 기준으로 쓰지 않는다.** 값은 **추출 경계와 정규화
  방식에 종속**된다 — 어디부터 어디까지 자르는지, 주석·공백을 어떻게 지우는지가
  조금만 달라도 값이 바뀐다. 문서에 적어야 할 것은 **분포**("전부 동일")와
  **추출 방식**(명령 그대로)이다. 값만 적으면 다음 사람이 재현하지 못하고
  **그 불일치를 사실의 불일치로 읽는다.**
  <br>*사례 — 백로그가 해시 값 두 개를 적었으나 검토자가 같은 대상에서 다른 값을 얻었고 앞의 값은 아예 재현되지 않았다. **결론(여러 벌이 전부 동일)은 양쪽이 일치했고 다른 것은 값뿐이었다.** 분포와 재현 명령으로 바꿔 적었다.*
  <br>▎**"통합을 막는 차이"라고 적힌 것을 그대로 믿지 않는다.** 앞 Task가 이월하며
  적어 둔 제약도 실측으로 재확인한다 — 근거가 언어 계약이면 문서보다 언어가 정본이다.
  <br>*사례 — 백로그가 "숫자 타입 분기 통일이 통합의 선행 조건"이라고 적었으나, 그 타입은 문자열 변환 인터페이스를 구현하고 포맷 함수가 그 변환을 부르므로 두 변종은 같은 문자열을 낸다. 15개 입력 대조에서 차이 0이었고, 제거 후 고정 출력 기준 파일도 그대로였다.*

- [ ] **WA-09 "복제"·"중복"을 정리하기 전에 각 선언의 사용처를 셌는가 — 통합 대상인지 삭제 대상인지 먼저 가른다**
  같은 값·같은 본문이 여러 곳에 있다는 관찰은 **복제와 죽은 선언을 구별하지 못한다.**
  정리 방향이 정반대다 — 복제면 통합(한 곳으로 모으기)이고, 죽은 선언이면 **삭제**다.
  각 선언이 **그 모듈의 프로덕션 코드에서 실제로 참조되는지** 세고 시작한다. 호출부가 0이면
  통합이 아니라 **삭제**다. 언어와 기본 도구가 미사용 선언을 오류로 잡지 않는 경우, 죽은 코드가
  "중복"으로 보이는 채 오래 남는다.
  <br>*사례 — 세 Task가 같은 함정에 빠졌다. 호출부가 **0건**인 같은 이름의 보조 파일 6개를 세 Task가 "통합 대상"으로 읽었다. 주석은 "다중 대상 경로에서 쓴다"고 적혀 있었으나 실제 호출이 없었다. 삭제 후 전체 빌드 rc=0이 호출부 부재의 증명이 됐다. 다른 Task에서는 한 증상으로 묶인 세 경로의 원인이 각각 달랐다. 또 다른 Task에서는 백로그가 "핵심 계층이 비공개로 두어 명령행 계층이 다시 선언한다"고 적었으나 **핵심 계층의 프로덕션 사용처가 0**이었고 명령행 계층이 유일한 소유자였다 — **승인된 계획이 착수 후 무효화됐다.***
  <br>▎게이트에 기대지 않는다. 미사용 선언 검사 도구는 죽은 **함수**를 잡지만
  **죽은 상수는 놓친다**(실측 — 4개가 rc=0을 통과했다).

- [ ] **WA-10 백로그의 선택지 구도(A/B·구현 방식)를 결론으로 읽지 않았는가**
  `{BACKLOG_FILE}`의 "선택지와 대가"는 **관찰 시점의 가설**이지 결론이 아니다. 세 가지를 의심한다.
  <br>**① A/B가 택일이 아닐 수 있다.** 두 선택지가 서로 다른 경로를 보고 있는데
  한 항목에 묶여 택일처럼 보이는 경우가 있다. **호출부를 세어 경로가 갈라져 있으면
  양립한다.**
  <br>**② 적힌 구현 방식이 새 중복을 만들 수 있다.** "X를 **본떠** Y를 신설"이라고
  적혀 있으면, 그 본문이 **몇 벌이 되는지** 먼저 센다. 백로그 항목
  상당수가 "같은 본문 N벌" 모양이 된 프로젝트가 있었다 — **백로그가 다음 Task에 만들 항목을 지금 만드는 것**이
  되면 안 된다. 판정·정책처럼 **한 곳이어야 하는 것**은 본뜨지 말고 한 구현을 공유한다.
  <br>*사례 — A안은 "쓰기용 경로 검증 함수를 본떠 읽기용을 신설", B안은 "읽기는 위협 모델이 다르다"였다. 실측 — 경로 해석 호출부 **2곳은 전부 쓰기**이고 읽기 로더 호출 **13곳은 전부 읽기**로 **이미 갈라져 있었다.** 쓰기에만 가드를 붙이니 B안의 반론이 유효한 채로 A안이 적용됐다(①). 구현은 본뜨는 대신 판정 술어만 공개해 공유했고, 판정을 반전시키는 mutation이 명령행 계층 20개 패키지를 깨 공유가 실제로 이어졌음이 확인됐다(②).*
  <br>**③ 적힌 대가(비용)가 코드와 다를 수 있다.** 백로그는 **관찰 시점의 코드**를 보고
  대가를 적는다. 그 사이의 Task가 **대가를 이미 지불했을 수 있다** — 필요한 인자가
  시그니처에 생겼거나, import가 이미 있거나, 테스트 이음매가 이미 놓였을 수 있다.
  **"비싸다"고 적힌 선택지를 버리기 전에 그 비용을 지금 코드에서 다시 센다.**
  <br>*사례 — A안의 대가가 "시그니처 변경 2곳 + 테스트 갱신"으로 적혀 있었다. 실측 — 두 실행 함수에 의존 객체 인자가 **이미 있고**, 필요한 import도 **이미 있고**, 테스트 이음매도 **이미 있었다.** 실제 변경은 **2줄**이다. 백로그는 "출력 대상을 **분리**해야 한다"에서 시그니처 변경을 상정했으나 **분리는 인자 하나를 감싸면 끝났다.** 대가 기재를 믿었다면 B(현상 유지)로 닫았을 것이고, 18곳은 출력 수준 설정을 따르고 2곳은 안 따르는 **비일관을 영구히 설명해야** 했다.*

  <br>▎**변이가 무효인 경우는 둘이다** — 컴파일되지 않는 변이(import가 안 쓰이게 됨 등)와,

  <br>*사례 — 한 Task에서 두 경우를 모두 겪었다. 컴파일되지 않는 변이가 있었고, 치환 패턴이 맞지 않아 변이가 적용되지 않은 채 테스트가 통과한 경우도 있었다.*

- [ ] **WA-15 mutation이 의도한 한 곳에만 적용됐는가 — 적용 범위와 대조군**

- [ ] **WA-17 세는 도구가 대상을 전부 보는지 확인했는가 — 과소와 과대 양쪽**

  교차검증**한다(등록 라인 수 ↔ 추출 수, 코드 ↔ 문서).
  <br>▎**세는 명령에 `head`·`tail`을 붙이지 않는다.** 화면을 줄이려고 자른
  출력을 **전수로 읽는 것**이 가장 흔한 경로다. 세는 것이 목적이면 `wc -l`이나
  `sort | uniq -c`로 **전량을 집계**하고, 눈으로 볼 때만 자른다 — 자른 출력과
  집계를 같은 단계에서 섞지 않는다.
  <br>*사례 — 한 헬퍼의 호출 지점을 검색해 나온 출력을 앞 15행으로 잘라 전수로 읽고 그 헬퍼를 **5벌**로 셌다. 실제는 **7벌**이고 두 모듈이 15행 밖에 있었다. 그 수치로 백로그를 등재했고 **재개 조건("7곳 이상")을 이미 넘긴 상태를 "미충족"으로 적었다** — 다음 Task가 착수하지 않을 기재였다. 다음 Task가 정정했다(5벌→7벌 · 6곳→8곳 · 26곳→36곳).*
  <br>▎**이 사례는 WA-16을 규범으로 올린 커밋과 같은 세션에서 났다.** 규범이
  있어도 그 순간에 적용되지 않으면 소용이 없다 — 그래서 처방을 "주의하라"가 아니라
  **금지할 명령**으로 적는다.
  <br>▎**수치로 처방을 정하는 프로젝트**("N곳"·"N벌"·"고유 N개"·계약 수치)에서는
  수를 잘못 세면 **틀린 것이 아니라 그럴듯하게 틀린** 계획이 승인된다.
  <br>*사례 — ① 기존 문서에서 플래그를 셀 때 마크다운 **전문**을 긁어, 옵션 표 밖 예제에 나온 다른 도구들의 옵션 **6건을 CLI 플래그로 셌다**(과대). 표 행만 보게 고쳐 걸러졌다. ② 기준 구현의 플래그를 `grep`으로 세어 **53개**를 얻었으나 선언 호출이 여러 줄에 걸친 **31건을 놓쳤다**(과소). 멀티라인 재집계로 **84개**였고, **놓친 31개 안에 기존 옵션 하나가 있었다** — 작업지시자가 누락된 기존 기능을 지적하지 않았다면 **이미 구현된 기능을 신규 누락으로 오판**한 채 계획이 승인됐을 것이다.*
  <br>▎**정규식 집계는 한 프로젝트에서 네 번 틀렸다** — 같은 원인의 사례 둘이
  이미 기록돼 있었고 이 사례가 셋째·넷째를 더했다.

- [ ] **WA-18 역검증이 침묵하면 테스트 자신의 단정부터 의심했는가**
  결함을 심었는데 조용하면 "그 경로가 실행되지 않는다"만 떠올리기 쉽다. 그러나
  **단정이 너무 느슨해 결함 상태의 출력도 만족시키는 경우**가 있다. 특히
  **부분 문자열 포함 검사**는 **대체 경로(폴백·다른 형식)의 출력**까지
  통과시킨다. 그런 테스트는 대조는 하지만 **어떤 결함도 잡지 못한다.**
  <br>▎처방 — **먼저 "그 분기의 출력이 맞는가"를 단정**한다(JSON이 아님·표 형태임 등).
  그다음 값을 본다. 폭·패딩처럼 형태에 실린 정보가 있으면 **그것까지 대조**한다.
  <br>*사례 — 목록 출력의 텍스트 형식 테스트가 텍스트 분기를 통째로 죽여도 **통과했다.** 숫자 리터럴을 부분 일치로만 찾았는데 **JSON 봉투 출력에도 같은 문자열이 있었다.** 역검증이 없었다면 "기본 출력 경로를 덮었다"고 보고했을 것이다. JSON 봉투 배제 + 폭 채움 대조를 넣어 고쳤다.*

- [ ] **WA-19 mutation이 침묵할 때 원인을 두 갈래로 갈랐는가 — 도달성 검사**
  역검증이 침묵했다고 곧바로 "테스트가 부실하다"고 결론내면 **호출 경로가 죽은 경우**를
  놓친다. 함수 본문 첫 줄에 **즉시 실패(예외 발생)** 를 심어 호출부 테스트가 실패하는지 본다.
  실패하면 코드는 실행되는 것이므로 원인은 검사 쪽(자기참조 WA-07 · 검증 부재)이고,
  조용하면 그 경로가 아예 실행되지 않는 것이다.
  <br>*사례 — 공통 패딩 함수에 즉시 실패를 심자 호출하는 패키지 3개가 모두 깨져 호출 경로가 살아 있음이 확인됐다. 이 확인이 없었다면 자기참조를 호출 경로 소실로 오진했을 것이다.*

- [ ] **WA-20 회귀 테스트가 수정 전 코드에서 실제로 실패하는가 — 실제 배선으로**
  경계 계층의 회귀 테스트를 **가짜 구현**에 연결하면 그 테스트는 매핑만 보고,
  고친 계층을 지나지 않는다. 그러면 **수정 전에도 통과**해 결함을 지키지 못한다.
  테스트를 먼저 쓰고 **수정 전 코드에서 RED를 실측해** Stage 보고에 적는다. 통과하면 테스트가
  결함 경로를 지나지 않는 것이다 — 실제 구현(바깥 의존부만 stub)에 연결해 다시 쓴다.
  <br>*사례 — 한 결함의 경계 계층 회귀 테스트가 가짜 서비스에 연결돼 수정 전 코드에서도 통과했다. 실제 서비스 구현에 연결하자 역검증 실패가 4건 → 6건으로 늘었다.*

- [ ] **WA-21 허용 집합 계약을 "나오는 모양"이 아니라 "거부되는 값"으로도 고정했는가**
  렌더 테스트는 허용한 형식이 **어떻게 나오는지**만 본다. 허용하지 않은 값이 **거부되는지**는 보지 않는다.
  허용 목록(출력 형식 · 열거형 옵션 값)은 **거부 케이스 1개 이상**으로 고정한다.
  <br>*사례 — 한 목록 명령은 csv·tsv 렌더 테스트가 모두 있었는데도, 그 명령이 선언한 허용 출력 형식 목록에 지원하지 않는 형식(`url`)을 끼워 넣어도 전부 통과했다 — 허용 집합이 넓어진 것을 아무 테스트도 보지 않았다. 독립 검토가 이를 잡았다.*

- [ ] **WA-22 같은 가드를 여러 호출 지점에 넣었다면, 지점 전수를 표 테스트로 고정했는가**
  helper 단위 테스트는 "가드가 맞게 판정하는가"만 본다. **"모든 지점이 가드를 부르는가"는 보지 않는다.**
  표의 대상은 "같은 helper를 부르는 곳"이 아니라 **"같은 성질을 가진 명령"**로 고른다.
  <br>*사례 — 공통 가드 helper에 단위 테스트와 2개 서비스 테스트가 있었다. 그런데도 나머지 지점은 호출을 빼도 아무 테스트도 실패하지 않았다. 루트 트리에서 지점 전수를 표로 돌리자 두 가지가 드러났다. 하나는 그 가드에 걸리는 **기존 안내 예시**였다(한 조회 명령의 오류 안내가 이제 거부되는 옵션을 권했다). 다른 하나는 독립 검토가 찾은 **누락 지점**(같은 가드가 필요한 다른 명령)이었다.*
  <br>▎**수정 확인용 변이는 helper 안이 아니라 호출 지점에 넣는다.**
  <br>*사례(재발) — 독립 검토 지적을 고치며 오류 문자열 변환 helper의 단위 테스트만 썼다. 호출 지점을 원래 오류 문자열 그대로 쓰도록 되돌려도 통과했다(rc=0). 보고서 생성 경로 테스트로 바꾸자 같은 변이에서 실패했다.*

- [ ] **WA-23 게이트 rc=0이 "안전"을 뜻한다고 읽지 않았는가**
  게이트는 저마다 **보는 범위가 정해져 있다.** 그 범위 밖은 rc=0이어도 검사되지
  않은 것이다. 이번 변경이 어느 게이트의 사각지대에 드는지 한 번 생각하고,
  들면 **수동 확인을 함께** 한다.
  <br>*사례 — 문서-코드 대조 스크립트는 플래그 **이름**만 대조한다. 문서 산문에 적힌 계약("경고를 낸다", "특정 형식은 지원하지 않는다")이 구현과 어긋난 채로 줄곧 rc=0을 통과하고 있었다.*

### B. 미해결·이월 항목을 남길 때 (가장 자주 빠뜨린다)

**"다음에 검토한다"는 인계가 아니다.** 아래 넷을 모두 만족해야 인계다.

- [ ] **WB-01 그 항목만 읽고 다음 Task가 수행할 수 있는가**
  배경(코드 근거 포함) · 현재 상태(실측) · 확인할 것(실행할 명령) · 선택지와 각각의 대가 ·
  예상되는 결과 · 판단 기준. 다른 문서를 먼저 읽어야 한다면 인계가 아니다.

- [ ] **WB-02 그 Task가 실제로 읽는 문서에 적었는가**
  `{DOC_ROOT}/plans/`는 "현재 단계만", `{DOC_ROOT}/report/`·`{DOC_ROOT}/working/`은 **다시 읽지
  않는다**(§7). 이월 항목은 `{DOC_ROOT}/spec/` 또는 `{DOC_ROOT}/orders/`에 둔다.
  <br>*사례 — 상수가 중복된 것을 발견했으나 구현계획서와 결과보고서에만 적었다 → 다음 Task가 읽는 문서가 아니었다 → 그 Task가 이를 발견할 경로가 없었다.*
  <br>▎**"닫은" 항목도 같은 취급이다.** 미해결을 남길 때만이 아니라 **하지 않기로
  결정했을 때**도 근거가 도달해야 한다. 닫기는 코드가 남지 않으므로 **문서가 유일한
  기록**이고, 근거가 없으면 다음 사람이 처음부터 다시 조사한다. 각 항목에
  **"다시 열어야 하는 조건"**을 함께 적는다 — 닫는 것과 지우는 것은 다르다.
  <br>*사례 — 한 항목을 제외하기로 한 근거가 단계 승인요약서에만 있었다 → 이후 Task의 단계가 같은 조사를 다시 해 이전 결론을 정정했고, 그다음 Task가 세 번째로 같은 것을 조사하다 백로그의 대가 기재가 틀렸음을 발견했다 → 같은 비용을 세 번 치렀다. 마지막 Task는 근거를 호출부 주석과 정본 설계 문서에 두고, 닫은 항목 전부에 재개 조건을 적었다.*

- [ ] **WB-03 로컬 재개 진입점에도 있는가**
  `{DOC_ROOT}/orders/` 또는 승인된 로컬 백로그(`{BACKLOG_FILE}`)에 이월·재개 조건을 기록한다. 이슈가
  있다면 `{ISSUE_TRACKER}`에서 참조할 수 있지만 작성·통신을 필수로 삼지 않는다.

- [ ] **WB-04 정하는 시점이 명시됐는가**
  "이후" · "나중에" · "여유가 되면"은 시점이 아니다. **어느 Task의 어느 절차**인지 적는다.
  그리고 그 Task의 범위 표에도 적는다.
  <br>*사례 — "다음 몇 개 Task에서 재검토한다"처럼 Task 범위만 적고 어느 절차인지 정하지 않았다 → 그것으로는 수행할 수 없다는 지적을 받았다.*

### C. 문서를 고쳤을 때

- [ ] **WC-01 그 문서를 인용하는 상위 문서를 역으로 갱신했는가**
  하위 문서를 보완하면 그것을 요약·인용한 승인요약서·결과보고서가 낡는다. 특히 **결과보고서
  작성 이후에 생긴 변경**은 잊기 쉽다.
  <br>*사례 — 추적 경로를 보완한 뒤 그것을 인용한 결과보고서에 반영하지 않았다 → 상위 문서가 낡았다 → 지적을 받았다.*

- [ ] **WC-02 정본 문서에 적은 것이 실제로 존재하는가**
  패턴 문서는 "이렇게 하기로 했다"를 적다가 **아직 만들지 않은 것을 만든 것처럼** 쓰기
  쉽다. 정본은 다음 Task가 그대로 따라 하므로 없는 것을 가리키면 안 된다.
  <br>*사례 — 패턴 문서가 공개 목록에 올린 헬퍼를 대표 구현 모듈에는 만들지 않았다 → 목록에 적힌 것이 실재하는지 확인하지 않았다 → 정본이 존재하지 않는 것을 가리켰다.*

- [ ] **WC-03 문서와 구현이 어긋났을 때, 어느 쪽이 정본인지 먼저 정했는가**
  드리프트를 발견하면 문서를 고치는 것이 반사적으로 빠르다. 그러나 **정본이 옳고
  구현이 틀린 경우**가 있다. 그때 문서를 구현에 맞추면 **결함을 계약으로 승격**시키는
  것이 된다. 정본 문서(`{CANONICAL_SPEC}`)인지 파생 문서(`{USER_DOCS_DIR}`)인지를 먼저 구분하고, 정본이 옳으면
  **구현을 고친다.**
  <br>*사례 — 정본이 "확장자로 형식을 추론하지 않는다"·"특정 확장자는 지원하지 않는다"를 정해 뒀는데 구현이 둘 다 어겼다 → 문서를 현실에 맞췄다면 결함이 그대로 계약이 됐을 것이다. 실제로는 정본을 한 글자도 고치지 않고 구현과 파생 문서를 정본에 맞췄다.*
  <br>▎**세 번째 경우가 있다 — 검사 도구가 틀릴 수 있다.** 문서와 구현이 둘 다
  맞는데 **게이트가 둘 사이를 어긋난 것으로 보고**하는 경우다. 이때 문서를 고치면
  **정확한 문서를 부정확하게 만든다.** 어긋남을 발견하면 세 후보를 모두 의심한다 —
  문서 · 구현 · **그것을 비교한 도구**.
  <br>*사례 — 금지어 게이트가 사용자 문서의 버전 문자열 예시를 구 버전 언급으로 잡았다 → 그 값은 버전 명령의 실제 출력 형식이었고 문서도 구현도 옳았다. 패턴이 버전 문자열의 일부를 삼킨 **과대 검출**이었다 → 문서를 고쳤다면 튜토리얼이 실제와 다른 예시를 싣게 됐을 것이다.*

- [ ] **WC-04 주석을 고쳐 쓸 때 줄 번호 인용을 남기거나 새로 쓰지 않았는가**
  설계 문서의 근거 표기 규칙(`경로::심볼`, 줄 번호 금지)은 설계 문서만이 아니라 **코드 주석**에도 해당한다.
  소스 파일:줄 번호 형태의 인용은 위에 한 줄만 더해져도 조용히 틀리고, 가리키는 선언을 지우면 허공을 가리킨다.
  `{LINEREF_GATE}`를 두는 프로젝트는 이를 CI에 넣고 테스트 파일도 검사 대상에 포함한다. 게이트가 없으면 주석을 손댈 때
  줄 번호 인용을 직접 검색한다. 주석을 손댈 때 그 주석의 줄 번호 인용을 심볼이나 사실 서술로 바꾼다.
  <br>*사례 — 고쳐 쓴 주석 두 곳이 줄 번호를 남기거나 새로 썼다 → 주석을 손대며 그 인용을 함께 정리하지 않았다 → 하나는 조정 세션 검토가, 다른 하나(지운 상수를 가리키는 인용)는 독립 검토가 잡았다. 프로젝트 전체에는 같은 표기가 여러 파일에 남아 있었다.*

- [ ] **WC-05 글을 스크립트로 일괄 치환했다면, 치환 뒤 문장을 사람이 읽을 수 있는지 따로 확인했는가**
  게이트(`{LINEREF_GATE}`)와 "주석만 바뀜" 검사는 **패턴이 사라졌는지**만 본다. **남은 문장이 말이 되는지**는 보지 않는다.
  치환은 문장을 두 갈래로 깨뜨린다.
  - 문서 언어의 문법 요소가 틀린다 — 한국어라면 조사(`구판를` · `구판가`)가 치환된 말의 받침과 어긋난다
  - 뜻 없는 꼬리가 남는다(남은 화살표 연결 · 빈 괄호 · 줄 맨 앞의 마침표)
  치환한 뒤에는 **문법 요소 스캔**(한국어는 받침 있는 말 뒤의 `를·가·와·는`)과 **구두점 스캔**을 돌리고, 표본을 직접 읽는다.
  <br>*사례 — 줄 번호 인용을 한 단어로 일괄 치환했다 → 게이트가 패턴 소멸만 확인해 통과했다 → 조사가 틀리고 뜻 없는 꼬리가 남은 문장이 여러 줄 나왔다. 조정 세션과 독립 검토(표본)가 각각 여러 줄을 찾았다.*

- [ ] **WC-06 같은 규칙을 문서와 코드 두 곳에 적지 않았는가 — 정본의 소유자**
  검사 규칙(정규식·임계값·목록)을 **정본 문서에 적고 게이트에도 적으면** 같은 본문이
  두 벌이 된다. 한쪽만 고치면 조용히 갈라지고, **어느 쪽이 정본인지 다음 사람이
  알 수 없다.** 실행되는 쪽(게이트)이 소유하고 **문서는 그것을 가리킨다** —
  게이트를 부르는 명령 한 줄이면 된다. 게이트를 호출하는 문서의 코드 블록도 규칙을 다시 적지 않고
  호출만 남긴다.
  <br>▎확인은 **명령으로** 한다. 규칙의 특징적인 조각을 양쪽에서 세어 **한 곳만
  1이고 나머지가 0**인지 본다.
  <br>*사례 — 문서 본문이 금지어 정규식을 직접 적고 있었다 → 게이트를 신설하며 게이트 정의에도 적었다면 같은 정규식 두 벌이 됐다. 백로그 항목 상당수가 "같은 본문 N벌" 모양이었던 프로젝트에서는 그때마다 통합 Task를 하나씩 썼다 → 본문의 정규식을 지우고 게이트 호출을 가리키게 한 뒤 `grep -c`로 게이트 정의 1 · 문서 0을 확인했다.*

- [ ] **WC-07 계약을 바꿨다면 사용자 문서를 개념어로도 전수 검색했는가**
  출력 형식·플래그·종료 코드 같은 **사용자 계약**을 바꾸면 명령 이름으로만 찾지 않는다.
  계약이 닿는 **개념 서술**(여러 대상 조회 같은 개념, 옵션명, 출력 구조, 종료 코드 표)에는 그 명령 이름이
  없는 경우가 많다. 찾은 서술의 예시는 **실측으로 다시 확인**한다 — 옆의 기존 예시가 틀려
  있을 수 있다.
  ```bash
  grep -rn "<명령명>" {USER_DOCS_DIR} README.md
  grep -rnE "<개념어1>|<옵션명>|<출력 필드>" {USER_DOCS_DIR} README.md
  ```
  <br>*사례 — 한 Task가 명령 이름으로 검색해 문서 두 개만 고쳤다 → 개념을 설명하는 절 둘과 README의 옵션 설명에는 그 명령 이름이 없어 빠졌다 → 다음 Task가 이를 고쳤다. 고치는 중 같은 절의 다른 명령 JSON 예시가 객체 형태로 적혀 있으나 실제 출력은 배열인, **원래부터 틀린** 예시도 드러났다.*

- [ ] **WC-08 설계 문서(`{DESIGN_DOC}`)의 불변조건·위험 지점·알고리즘을 고쳤다면, 작성자가 아닌 검토자가 코드와 대조했는가**
  설계 문서는 **다음 사람이 코드를 고치는 근거**가 된다. 서술이 코드와 반대면 문서를 믿은 사람이
  **올바른 코드를 결함으로 보고 고친다** — 틀린 문서가 없는 문서보다 위험하다. 쓴 사람은 자기 서술을
  코드에서 다시 "확인"하기 쉽다. 표본 주장을 골라 코드와 대조하게 하고, 지적은 **코드로 확인한 뒤**
  반영한다(검토자도 틀린다). `{DESIGN_REFS_GATE}`는 이름의 실재만 보므로 이 검토를 대신하지 못한다.
  <br>*사례 — 설계 문서 초안이 목록 조회 페이징을 "필터는 페이징이 끝난 뒤"라고 적고 "필터를 루프 안으로 옮기면 위험"이라고 경고했다 → 실제 코드는 이미 루프 안에서 필터하고 종료 판정만 필터 전 배치로 센다 — 올바른 현재 구조를 위험으로 표시한 것이다. 독립 검토가 이것을 포함해 여러 건을 잡았고, 검토자의 지적 하나(기전 설명)는 코드로 반증해 기각했다.*

## 8. 문서 체계

`{DOC_ROOT}`는 끝 구분자(`/`) 없이 바인딩한다.

```
{DOC_ROOT}/
├── orders/           # 오늘할일 — 새 세션에서 "지금 뭘 해야 하지?" 답
├── plans/            # 수행계획서 + 구현계획서 — "어떻게 할 것인가"
│   └── archives/     # 완료된 계획서 보관 (이동 시점은 프로젝트가 정한다)
├── working/          # 작업 단위별 완료보고서 + 단계 승인요약서 — "어디까지 했는가"
├── report/           # 최종 결과보고서 — "결과가 무엇인가"
├── feedback/         # 코드 리뷰 피드백 — "무엇이 틀렸는가" (AI가 스스로 만들 수 없는 문서)
├── tech/             # 기술 사항 정리 — "무엇을 발견했는가" (세션 간 지식 영구화)
├── spec/             # 설계 사항 정리 — "무엇을 기반으로 하는가" (세션 간 지식 영구화)
└── troubleshootings/ # 트러블슈팅 — "이 함정에 다시 빠지지 마라"
```

**왜 문서가 필요한가**: AI는 세션이 끊기면 기억이 사라진다. 문서가 있으면 새 세션에서도 컨텍스트 전달 없이 `orders/` → 로드맵 → `plans/`(현재 단계) → `working/`(직전 Stage Summary) 순으로 읽어 즉시 작업 재개가 가능하다.

### 문서 역할

| 폴더 | 목적 | 다음 세션에서 읽는가 |
|------|------|----------------|
| orders | 현재 해야 할 일 | 항상 |
| 로드맵(`{ROADMAP_FILE}`) | 전체 Task의 범위·의존·결과 | 항상(세션 시작 때 현황 파악) |
| plans | 다음 작업 기준 | 현재 단계만 |
| working | 진행 기록 | 직전 Stage Summary만 |
| report | 최종 결과 | 종료 후만 |
| feedback | 사람 리뷰 | 필요 시 |
| tech | 영구 지식 | 필요 시 |
| spec | 영구 설계 | 필요 시 |
| troubleshootings | 영구 교훈 | 필요 시 |

### 파일명 규칙

아래 표의 자리는 모두 `{DOC_ROOT}` 기준 전체 경로 패턴으로 바인딩한다(폴더는 위 구조를 따른다). 사후 기록 `{POSTMERGE_RECORD}`도 같다. 예시는 형식을 보이기 위한 것이며 실제 경로는 적용 문서가 정한다.

| 문서 | 경로 패턴 | 예시 |
|------|-----------|------|
| 오늘할일 | `{ORDERS_FILE}` | `{DOC_ROOT}/orders/<YYYYMMDD>.md` |
| 수행 계획서 | `{PLAN_FILE}` | `{DOC_ROOT}/plans/<N>_plan.md` |
| 구현 계획서 | `{IMPL_PLAN_FILE}` | `{DOC_ROOT}/plans/<N>_impl.md` |
| 단계별 완료보고서 | `{STAGE_REPORT_FILE}` | `{DOC_ROOT}/working/<N>_<작업단위>_stage<S>.md` |
| 단계 승인요약서 | `{STAGE_SUMMARY_FILE}` | `{DOC_ROOT}/working/<N>_stage<S>_summary.md` |
| 진행현황 | `{PROGRESS_FILE}` | `{DOC_ROOT}/working/progress.md` |
| 최종 보고서 | `{REPORT_FILE}` | `{DOC_ROOT}/report/<N>_report.md` |
| 피드백 | `{FEEDBACK_FILE}` | `{DOC_ROOT}/feedback/<N>_review.md` |
| 사후 기록(로컬, 커밋하지 않음) | `{POSTMERGE_RECORD}` | `{DOC_ROOT}/working/<N>_postmerge.md` |
| 기술 정리 | `{DOC_ROOT}/tech/` 아래 주제별 자유 명명 | `http_client_timeout.md` |
| 설계 정리 | `{DOC_ROOT}/spec/` 아래 주제별 자유 명명 | `retry_policy.md` |
| 트러블슈팅 | `{DOC_ROOT}/troubleshootings/` 아래 주제별 자유 명명 | `stale_cache_bug.md` |

### 파일 작성 원칙

- **Stage Summary**는 다음 세션에서 읽는 대표 문서다
- **Progress**는 작업 전체의 진행 현황만 누적 관리한다
- **완료보고서**는 작업 단위별 상세 기록으로 유지한다
- **Report**는 최종 결과만 기록한다
- **영구 지식**은 `{DOC_ROOT}/tech/`, `{DOC_ROOT}/spec/`, `{DOC_ROOT}/troubleshootings/`에만 승격한다
- 진행현황(`{PROGRESS_FILE}`)·피드백(`{FEEDBACK_FILE}`)은 선택 문서다. 쓰는 프로젝트는 갱신 시점·작성 주체를 적용 문서에 정한다(피드백 = 사람 리뷰·독립 검토 결과)

## 10. Git·병합·보안·테스트 공통 원칙

### 로컬 CI — 정식 Task의 최종 검사

- 정식 Task의 최종 검사는 절차 11~13 뒤 격리 병합 후보에서 `{TASK_CI_CMD}`로 수행한다. `{CI_CMD}`는 일반 CI이며 정식 Task 여부를 단독으로 보증하지 않는다. 그 전의 Stage 검증은 개별 게이트를 `{TEST_RUNNER}`로 돌린다
- 이슈·PR 통신은 필수 조건이 아니다. 다만 컨테이너 이미지나 도구 캐시가 없으면 해당 준비에 네트워크가 필요할 수 있으므로 전체 CI의 무조건적인 오프라인 성공을 보장하지 않는다. 준비가 안 됐으면 실패·미실행으로 기록한다
- 후보 SHA·tree와 `{TASK_CI_CMD}` 결과를 `{POSTMERGE_RECORD}`에 남긴다. 원격 체크 표시는 필수 조건이 아니다
- **CI가 도는 동안 같은 브랜치에 커밋하지 않는다**(보조 에이전트 커밋 포함) — CI 결과가 시작 시점 후보와 어긋난다(예: 시작 커밋과 HEAD를 비교하는 단계가 있으면 그 단계가 실패한다). 보고서와 모든 커밋은 후보 CI 전에 끝낸다. 이후 후보가 바뀌면 전체 CI를 다시 수행하고 사후 사실은 별도 로컬 기록에 남긴다
- 원격 CI 호스트의 실행 정책(과금·자동 실행 여부 등)은 `{CI_HOST_POLICY}`를 따른다
- 원격 CI의 수동 실행·트리거 변경은 `{CI_HOST_POLICY}`가 허용한 주체만 하며 보조 에이전트에 맡기지 않는다

*사례 — CI 실행 중 같은 브랜치에 커밋이 들어갔다 → 시작 시점 커밋과 HEAD를 비교하는 검사 단계가 불일치로 실패했다 → 전체 CI를 다시 돌려 약 4분을 잃었다.*

### 브랜치·커밋 정책

- 브랜치: `{BRANCH_PATTERN}`. 로컬 Task 번호를 고유하게 관리하며(`{TASK_ID_FORMAT}`) 이슈(`{ISSUE_TRACKER}`)와 일치할 필요는 없다
- force push 금지
- 작은 Task를 마치거나 자동 수정이 성공할 때마다 의미가 분명한 메시지로 커밋한다. 다음 변경이 문제를 일으켜도 즉시 되돌릴 수 있는 체크포인트를 확보한다
- 커밋 메시지 형식: `{COMMIT_FORMAT}`
  - 타입: `{COMMIT_TYPES}`
  - 첫 줄 끝에 Task 번호를 붙인다. 커밋만 보고도 어느 로컬 Task의 산출물인지 추적된다
  - breaking change 표기와 타입별 버전 증가 폭은 `{VERSIONING_DOC}`를 따른다
- `{SECRET_FILE}` 커밋 금지, 대용량 바이너리 커밋 금지

### 병합 정책

1. 모든 Stage와 최종 보고 승인을 받고, 절차 12·13을 마친 Task 브랜치를 경로 지정으로 커밋한다. 기존 사용자 변경은 포함하지 않는다.
2. 원본 `{MAIN_BRANCH}`와 Task 브랜치(`{BRANCH_PATTERN}`)의 SHA를 기록한다. 별도의 일반 clone에서 `{MAIN_BRANCH}`·Task refs를 해당 SHA로 고정한다. 실제 `{SECRET_FILE}`이나 ignored 입력 없이 detached `{MAIN_BRANCH}`에서 `git merge --no-ff <Task 브랜치>`로 후보를 만든다. 충돌은 검토 후 해결하고 후보를 다시 검증한다.
3. 후보 clone 최상위에서 `{TASK_CI_CMD}`를 실행한다. 후보 첫째·둘째 부모와 clone의 `{MAIN_BRANCH}`·Task ref, 결과보고서 본문·`{REPORT_HTML_POLICY}`에 따른 HTML·로드맵을 검증한 뒤 `{CI_CMD}` 전체를 수행하는 명령으로 바인딩한다(이 기능이 없으면 빠진 검사를 사람이 수동으로 확인해 기록한다). CI 전후 HEAD·tree 및 작업 트리를 검사한다. 후보·tree·부모·명령·결과와 CI의 SKIP을 기록한다. 이 기계 검사는 실제로 별도 clone을 생성했는지, 원본 refs와 일치하는지, 내용의 정확성·승인이나 외부 환경 전체의 불변성을 보증하지 않는다. clone 생성과 원본 SHA 대조는 사람이 별도 확인한다.
4. 원본 `{MAIN_BRANCH}`·Task SHA를 다시 대조한다. 확인한 후보 객체를 원본으로 가져오고 `{MAIN_BRANCH}`가 다른 worktree에서 사용 중이지 않을 때 별도 임시 worktree에서 `git merge --ff-only <검증된 후보 SHA>`로 반영한다. 충돌·다른 worktree 사용·작업 트리 오염·기준 변경 시 중단한다. 반영된 SHA·tree를 후보와 다시 대조한다. 객체 반입과 `{MAIN_BRANCH}` 변경도 실제 적용 승인 범위에 따른다.
5. 원격 반영은 별도 상태다. fetch와 push의 실제 URL이 각각 하나이고 서로 같은지 확인하고(예: `git remote get-url --all origin` · `git remote get-url --push --all origin` · URL 재작성 규칙은 `git config --get-regexp 'url\..*\.insteadof'`), 확인할 수 없거나 다중 대상·명시 push refspec이 있으면 중단한다. 같은 대상의 `{MAIN_BRANCH}`를 fetch하여 원격 tip이 검증된 로컬 `{MAIN_BRANCH}`의 조상인지 확인한다. 조회 실패·분기·거부 시 force 없이 중단한다. 원격 설정과 URL 재작성 규칙이 검사 중 바뀌지 않도록 단독 작업한다. push 직전 fetch·push URL, 다중 설정·refspec을 다시 비공개로(URL을 화면·기록에 출력하지 않고 일치 여부만 확인) 비교하고 불일치 시 중단한다. `git push --no-follow-tags --no-recurse-submodules <검증한 원격> <검증 SHA>:refs/heads/{MAIN_BRANCH}`(`<검증한 원격>`은 fetch·push URL을 대조한 그 원격)의 일반 push 뒤 같은 대상의 원격 SHA를 재조회한다. URL·인증정보·원격 오류 원문은 기록하지 않는다. 검사와 push 사이에 다른 프로세스가 Git 설정을 바꾸는 경합은 이 수동 절차로 원자적으로 차단할 수 없으므로, 단독 작업을 보장할 수 없다면 push하지 않는다.
6. 일반 push는 조회와 push 사이에 발생한 모든 원격 전진을 거부하지는 않는다. push 성공 후 조회 실패는 `push 성공·최종 원격 상태 미확인`, 조회 결과가 다르면 `push 후 원격 SHA 상이·원인 미확인`으로 기록한다. 원격 반영 실패는 로컬 승인·CI 결과를 지우지 않는다.

후보 CI 전 마지막 커밋의 `{ORDERS_FILE}`에는 완료 판정을 적을 위치(사후 기록)만 미리 적는다. CI·반영 결과와 완료 판정은 커밋하지 않는 `{POSTMERGE_RECORD}`에 적는다(§5 「완료 선언 전 전수 확인」). 로컬 `{MAIN_BRANCH}` 반영 직후와 원격 반영 시도 직후의 상태는 임시 worktree가 아닌 **원본 작업 디렉터리**의 `{POSTMERGE_RECORD}`에 별도로 기록한다. 검증 후보·로컬 `{MAIN_BRANCH}` SHA와 tree, 시도 시각, 원격 반영 성공·실패·미확인 및 재조회 결과, Git에서 복원되지 않는 관찰·판단을 구분한다. URL·자격증명은 쓰지 않는다. 기록은 후보 커밋을 바꾸지 않으며 로컬 미커밋 파일이므로 별도 백업·인계한다. 백업 위치와 복구 가능성을 확인한 뒤 임시 worktree를 정리한다. 새 clone에는 자동 전파되지 않는다. 다음 정식 Task 절차 4(조사)에서 사후 사실의 정본 반영 여부를 검토한다. 이슈 트래커 댓글이나 기록 브랜치를 필수로 삼지 않는다.

시크릿은 항상 환경변수 또는 `{SECRET_FILE}`(gitignore 대상)에서 읽는다. 프로젝트의 환경변수 규약은 `{SECRET_ENV_CONVENTION}`을 따른다.

- 버그 수정 = 회귀 테스트 추가

### 디렉터리 배치 — 최상위 폴더 최소화

**프로젝트 최상위에는 가능한 한 파일을 만들지 않는다.** 새 파일은 용도별 하위 디렉터리에 둔다.

| 용도 | 위치 |
|---|---|
| 배포·컨테이너 자산, 실행 스크립트, 소스 코드 | 프로젝트가 정한 용도별 하위 디렉터리 |
| 사용자 문서 | `{USER_DOCS_DIR}` — 아래 수록 기준 참조 |
| 작업 문서 | `{DOC_ROOT}` |
| 버전 관리 문서 — **최상위 예외** | `{VERSIONING_DOC}`와 사용자용 변경 이력 파일(관례 위치, 최상위) — 사용자 문서 폴더에 두면 현재 계약만 서술 원칙의 금지어와 충돌한다 |

#### 사용자 문서 수록 기준

**`{USER_DOCS_DIR}`에는 최종 결과물을 사용하는 데 직접 필요한 문서만 둔다.** 둘 중 하나여야 한다.

1. 결과물의 **기능**을 설명한다 (사용법·입출력 형식·사용 예)
2. 결과물의 **동작 개념**을 설명한다 (도메인 용어, 핵심 개념)

여기에 해당하지 않는 문서는 전부 `{DOC_ROOT}` 아래 적절한 경로에 둔다.

| 성격 | 위치 |
|---|---|
| 개발 이력·감사 기록 | `{DOC_ROOT}/tech/` |
| 설계 근거·정본 | `{DOC_ROOT}/spec/` |
| 함정·트러블슈팅 | `{DOC_ROOT}/troubleshootings/` |
| 계획·진행·보고 | `{DOC_ROOT}/plans/`, `{DOC_ROOT}/working/`, `{DOC_ROOT}/report/` |

판단 기준: **결과물 사용자가 읽을 이유가 있는가.** 개발자만 읽는 문서는 `{USER_DOCS_DIR}`에 두지 않는다.

루트 README도 사용자 문서로 보아 같은 서술 원칙·검사 대상에 넣는다.

*사례 — 소스 저장소의 개발 이력 문서가 사용자 문서 폴더에 들어 있었다 → 사용자가 읽을 이유가 없는 문서였다 → 작업 문서의 기술 정리 폴더로 옮겼다.*

#### 사용자 문서는 현재 계약만 서술한다

**사용자 문서는 결과물을 처음 보는 사람이 읽는 문서다. 이전 버전이 사용자에게 배포된 적 없으면 존재하지 않는 셈 친다.**

독자가 본 적 없는 이전 버전과 비교하면 **혼란만 는다.** 사용자 문서와 사용자에게 노출되는 도움말에는 현재 계약만 쓴다.

| 금지 | 대신 |
|---|---|
| "이전 버전에서는 A였다" | 현재 B만 설명한다 |
| "A에서 B로 개명" | B가 무엇인지만 쓴다 |
| "이 별칭은 삭제됨" | 언급하지 않는다 |
| "breaking change" · "마이그레이션" · "deprecated" | 쓰지 않는다 |
| 내부 구현 사정 (내부 함수·훅 이름) | 사용자에게 필요한 규칙만 쓴다 |
| 이전 버전·내부 문서 경로·결정/Stage 번호 (도움말 포함) | 쓰지 않는다 |

이전 버전 사용자가 있는 프로젝트는 호환·이행 안내를 `{VERSIONING_DOC}`(또는 사용자용 변경 이력 문서)에 두고 사용자 문서 본문은 현재 계약만 서술한다.

내부 귀착 기록(변경 이력·귀착 근거)은 `{DOC_ROOT}/spec/`에 둔다. 같은 사실이 두 곳에서 다른 목적을 갖는다 — 사용자 문서는 **무엇을 할 수 있는가**, `{DOC_ROOT}/spec/`은 **무엇이 어디로 갔는가**. 금지어 검사를 `{FORBIDDEN_WORDS_GATE}`로 자동화한 프로젝트는 그 게이트가 판정한다.

#### 루트에 두는 파일

루트에 두는 것은 **도구가 루트에서만 인식하는 파일**로 한정한다. 예: 빌드 진입 파일, 언어 모듈 정의 파일, ignore 파일, 컨테이너 구성 파일, `{AGENT_INSTRUCTIONS_FILE}`, `ALIGNS.md`, README. 각 파일이 루트에 있어야 하는 근거는 프로젝트가 기록한다.

### 코드 품질 기준

- 함수는 작게 (50줄 미만)
- 파일은 집중되게 (일반 200~400줄, 최대 800줄)
- 깊은 중첩 금지 (4단계 초과 금지)
- 값을 제자리에서 바꾸지 말고 새 값 반환(불변성)
- 디버그 출력 잔존 금지
- 하드코딩된 값 금지
