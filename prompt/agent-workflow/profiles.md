# 작업 강도 프로필

[workflow.md](workflow.md)는 **dev** 프로필을 기준으로 쓴 문서다. 프로젝트는 아래 세 프로필 중 하나를 골라 적용 문서 **머리 기록란의 「작업 강도 프로필」** 칸에 적는다. 프로필은 workflow.md의 절차를 **바꾸는 차이만** 정한다. 적지 않은 부분은 workflow.md를 그대로 따른다.

- 우선순위: 적용 문서 > 채택한 프로필의 차이 > workflow.md. workflow.md §5의 "절차를 건너뛰지 않는다"는 채택한 프로필이 바꾼 절차에는 적용하지 않는다.

- `{자리_이름}`의 의미는 [project_template.md](project_template.md) 바인딩 표에 있다.
- 안전 원칙(workflow.md §10의 보안·비밀 규칙, 되돌리기 어려운 작업의 사전 승인)은 어느 프로필에서도 줄이지 않는다.

## 프로필 선택

| 프로필 | 쓰는 경우 |
|---|---|
| **dev**(기본) | 코드를 바꾸고, 사람이 단계마다 방향을 확인해야 하는 개발 프로젝트 |
| **dev-fast** | 코드를 바꾸지만, 사람의 확인을 계획과 최종 결과로 줄이고 중간 검토를 독립 에이전트에게 맡기는 프로젝트 |
| **standard** | 코드 변경보다 조사·분석·문서·운영 업무가 중심인 프로젝트 |

## 차이표

| 항목(workflow.md 위치) | dev | dev-fast | standard |
|---|---|---|---|
| Task 브랜치(§5 절차 3) | 만든다(`{BRANCH_PATTERN}`) | 만들지 않아도 된다 | 저장소 변경이 있을 때만 |
| 외부 이슈(§5 절차 1) | 선택(`{ISSUE_TRACKER}`) | 쓰지 않음 | 선택 |
| 수행계획서·구현계획서(§5 절차 5·6) | 둘 다 작성, 각각 작업지시자 승인 | 둘 다 작성. 구현계획서는 **서로 다른 관점의 독립 에이전트 검토**를 거친 뒤 작업지시자 승인 | 설계와 실행 절차를 따로 검토해야 할 만큼 복잡할 때만 나눈다. 평소에는 목표·범위·완료 조건·순서를 담은 짧은 작업 기록 하나로 대신한다 |
| Stage 승인(§5 절차 9·10) | 작업지시자가 Stage Summary로 승인 | **메인 에이전트**가 Stage Summary를 작성·검토하고 진행한다. 작업지시자 승인은 받지 않는다 | 방향 선택이나 중요한 변경이 있을 때만 승인받는다 |
| 검증 종료 조건(§6) | §6 품질 게이트의 확인 항목과 「완료 판정 시 블로커」를 모두 해소 | dev 조건에 더해, 구현하지 않은 **별도 에이전트 인스턴스**가 검증한다. 지적을 반영한 뒤 **새 인스턴스**로 한 번 더 검증한다(총 2회). 수행계획서·구현계획서도 같은 방식으로 독립 검토를 받는다 | 업무에 맞는 검증(출처 대조, 실제 대상에서 적용 결과 확인) |
| 최종 결과보고서 퀴즈(§9) | `{REPORT_QUIZ_REQUIRED}` = 필수 | `{REPORT_QUIZ_REQUIRED}` = 「없음 — dev-fast 프로필」 | `{REPORT_QUIZ_REQUIRED}` = 「없음 — standard 프로필」 |
| 간단하고 되돌리기 쉬운 작업 | §5 절차 적용 | §5 절차 적용 | 요청 이해 → 필요한 조사 → 수행 → 검증 → 결과 보고로 바로 처리한다. 계획서·승인요약서·서브 에이전트·새 세션을 강제하지 않는다 |

## 프로필과 무관하게 유지하는 것

- 영향이 크거나 되돌리기 어려운 작업(운영 장애, 데이터 손실, 보안·권한 변경, 외부 게시, 비용 발생)은 실행 전에 대상·변경·영향·검증·복구 방법을 제시하고 작업지시자 승인을 받는다.
- 실패, 부분 성공, 미검증은 완료로 표시하지 않는다.
- AI의 추천·요약·다른 에이전트의 보고는 사람의 승인을 대신하지 않는다.
- Task마다 루트 `ALIGNS.md`로 작업 결과의 기준을 정하고 결과를 대조한다([alignment.md](alignment.md)). 계획서를 쓰지 않는 간단 작업은 결과 보고에 대조를 짧게 적는다.
