현재 저장소의 코드를 분석해서 `DESIGN.md`를 작성하라.

목표는 일반적인 아키텍처 문서를 만드는 것이 아니다.  
이 문서는 **코드를 직접 읽지 않아도 현재 구현의 핵심 아이디어, 자료구조, 알고리즘, 불변조건, 구현 기법, 트레이드오프를 사람이 이해할 수 있게 설명하는 문서**여야 한다.

특히 AI 에이전트가 이후 코드를 수정할 때 반드시 유지해야 하는 설계 의도를 명확하게 기록하라.

## 작업 원칙

1. 실제 코드에 존재하는 내용만 기록한다.
2. 추측하지 않는다.
3. 확인할 수 없는 내용은 `Unknown` 또는 `확인 필요`라고 표시한다.
4. 코드의 함수와 클래스를 단순히 나열하지 않는다.
5. "무엇을 하는가"보다 "왜 이렇게 구현되어 있는가"를 우선해서 설명한다.
6. 자료구조, 상태, 데이터 흐름, 알고리즘, 캐시, 동시성, 파일 형식, 프로토콜을 중점적으로 분석한다.
7. 코드에서 암묵적으로 유지되고 있는 불변조건을 찾아 명시한다.
8. 성능 또는 메모리 최적화를 위한 구현 기법이 있으면 반드시 설명한다.
9. 변경하면 위험한 부분과 결합도가 높은 부분을 명확하게 표시한다.
10. 각 중요 설명에는 근거가 되는 파일 경로와 함수, 클래스 또는 심볼을 기록한다.
11. 테스트가 어떤 설계 원칙을 검증하는지 연결한다.
12. 현재 구현과 문서가 충돌하면 코드를 기준으로 작성하되 `Documentation Gap`으로 표시한다.

## 먼저 수행할 분석

저장소 전체를 살펴보고 다음을 파악한다.

- 주요 실행 진입점
- 핵심 모듈
- 주요 데이터 구조
- 상태를 보유하는 위치
- 데이터 흐름
- 외부 시스템과의 경계
- 핵심 알고리즘
- 캐시 또는 인덱스
- 동시성 또는 비동기 처리
- 영속성 방식
- 오류 처리 방식
- 중요 테스트
- 변경 위험도가 높은 코드

README 또는 기존 문서만 읽고 작성하지 말고 실제 구현 코드를 확인한다.

## DESIGN.md 구조

다음 형식을 기본으로 사용한다.

# Design

## 1. Purpose

이 소프트웨어 또는 컴포넌트가 해결하는 핵심 문제를 설명한다.

## 2. Mental Model

개발자가 이 시스템을 이해하기 위해 머릿속에 가져야 하는 가장 단순한 모델을 설명한다.

가능하면 다음 형태의 ASCII 다이어그램을 포함한다.

```text
Input
  |
  v
Parser
  |
  v
Internal State
  |
  v
Processor
  |
  v
Output
```

## 3. Core Concepts

시스템을 이해하는 데 필요한 핵심 개념을 설명한다.

각 개념은 다음 형식으로 작성한다.

### Concept Name

- 역할:
- 존재 이유:
- 주요 구현:
- 관련 코드:

## 4. Data Structures

핵심 자료구조를 설명한다.

각 자료구조마다 다음을 포함한다.

- 저장하는 데이터
- 자료구조를 선택한 이유
- 데이터 소유권
- 다른 자료구조와의 관계
- 시간 복잡도
- 공간 복잡도
- 변경 시 주의점

## 5. Data Flow

주요 처리 흐름을 단계별로 설명한다.

예:

```text
Request
 -> Validation
 -> Parse
 -> State lookup
 -> Processing
 -> Persistence
 -> Response
```

가능하면 실제 함수 또는 모듈 이름을 연결한다.

## 6. Core Algorithms

중요 알고리즘을 설명한다.

코드를 그대로 번역하지 말고 다음을 설명한다.

- 입력
- 출력
- 처리 원리
- 주요 단계
- 시간 복잡도
- 메모리 특성
- 경계조건

## 7. Invariants

코드가 정상적으로 동작하기 위해 항상 참이어야 하는 조건을 작성한다.

예:

- ID는 프로세스 생명주기 동안 중복되지 않는다.
- 인덱스에 존재하는 객체는 반드시 primary store에도 존재한다.
- 상태가 `COMPLETED`이면 다시 `RUNNING`으로 돌아갈 수 없다.

가능하면 해당 invariant를 검증하는 테스트를 함께 연결한다.

## 8. Implementation Techniques

일반적인 구현이 아닌 특별한 구현 기법을 설명한다.

예:

- 메모리 중복 제거
- lazy initialization
- copy-on-write
- batching
- zero-copy
- object pooling
- caching
- index
- lock-free 처리
- optimistic locking
- retry/backoff
- deduplication

각 기법에 대해 왜 사용했는지 설명한다.

## 9. State Management

상태가 어디에서 생성되고 변경되고 제거되는지 설명한다.

특히 다음을 확인한다.

- source of truth
- 파생 상태
- 캐시
- 영속 상태
- 임시 상태

## 10. Concurrency Model

동시성이 존재하는 경우 다음을 설명한다.

- thread/process/task 모델
- 공유 상태
- lock
- race condition 방지
- ordering guarantee
- atomicity

동시성이 없다면 그 사실을 명시한다.

## 11. Failure Model

실패 상황과 복구 방식을 설명한다.

- 예상 가능한 실패
- retry 여부
- partial failure
- 데이터 손상 가능성
- crash recovery
- idempotency

## 12. Performance Characteristics

성능에 영향을 주는 주요 요소를 설명한다.

- 주요 hot path
- CPU 비용
- 메모리 비용
- I/O
- 네트워크
- 알고리즘 복잡도
- 병목 가능성

측정되지 않은 성능 수치를 임의로 작성하지 않는다.

## 13. Trade-offs

현재 구현이 선택한 방식과 대안을 설명한다.

형식:

### 선택

현재 구현 방식

### 이유

이 방식을 선택한 이유

### 대안

가능했던 다른 방식

### 비용

현재 선택으로 인해 발생하는 단점

## 14. Dangerous Changes

AI 에이전트 또는 개발자가 수정할 때 특히 주의해야 하는 부분을 작성한다.

예:

- 이 자료구조를 다른 구조로 변경하면 ordering guarantee가 깨질 수 있다.
- 이 캐시는 단순 성능 최적화가 아니라 correctness에 영향을 준다.
- 이 함수 호출 순서는 외부 프로토콜 요구사항이다.

## 15. Tests as Design Specification

중요 테스트와 해당 테스트가 보호하는 설계 원칙을 연결한다.

| 테스트 | 보호하는 설계 |
|---|---|
| test_xxx | 중복 ID 방지 |
| test_yyy | crash recovery |
| test_zzz | ordering guarantee |

## 16. Modification Guide

다음 유형의 변경 시 확인해야 하는 코드를 설명한다.

- 새로운 기능 추가
- 데이터 구조 변경
- 저장 형식 변경
- API 변경
- 성능 최적화
- 동시성 변경

## 17. Known Limitations

현재 구현에서 의도적으로 허용하고 있는 제한 사항을 설명한다.

## 18. Documentation Gaps

코드만으로 설계 의도를 확정할 수 없는 부분을 기록한다.

## 중요한 출력 원칙

`DESIGN.md`는 다음과 같은 문서가 되어서는 안 된다.

- 소스 코드 파일 목록
- 클래스 목록
- 함수 목록
- README 복사본
- API 명세서
- 일반적인 아키텍처 설명

다음 질문에 답할 수 있어야 한다.

> "이 코드를 처음 보는 숙련된 개발자가 DESIGN.md만 읽은 뒤 핵심 구현을 안전하게 수정할 수 있는가?"

답이 아니라면 문서를 보완한다.

마지막으로 전체 문서를 검토해서 다음 항목을 확인한다.

- 구현 근거가 없는 추측이 없는가?
- 중요한 invariant가 빠지지 않았는가?
- 핵심 자료구조의 선택 이유가 설명되어 있는가?
- 성능 관련 설계 의도가 기록되어 있는가?
- 테스트와 설계가 연결되어 있는가?
- AI 에이전트가 잘못 변경하기 쉬운 부분이 명확한가?
