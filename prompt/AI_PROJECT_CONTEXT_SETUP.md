# 프로젝트 AI 문서 체계 구축

현재 프로젝트를 분석하여 앞으로 새로운 AI 에이전트가 최소한의 컨텍스트만으로도 프로젝트를 정확하게 이해하고 작업을 이어갈 수 있도록 다음 문서 체계를 구축하라.

- `ARCHITECTURE.md`
- `DESIGN.md`
- `HANDOFF.md`
- 기존 `AGENTS.md`의 문서 참조 규칙

문서를 먼저 작성하지 말고 실제 저장소를 충분히 조사한 후 작성한다.

## 1. 프로젝트 조사

먼저 다음을 조사한다.

- 디렉터리와 주요 파일 구조
- 실행 진입점
- 주요 컴포넌트와 각각의 책임
- 컴포넌트 사이의 호출 및 데이터 흐름
- 데이터 저장 위치와 소유권
- 외부 시스템 및 API 연동
- 설정 및 환경변수
- 빌드, 실행, 배포 구조
- 테스트 구조
- 주요 데이터 구조와 알고리즘
- 코드에서 확인되는 중요한 invariant와 제약조건
- 현재 진행 중인 작업
- Git history에서 확인할 필요가 있는 주요 설계 변경

README나 기존 문서만 신뢰하지 말고 실제 코드, 설정, 테스트와 비교하여 현재 구현을 기준으로 판단한다.

확인되지 않은 내용을 추측하여 문서화하지 않는다. 추론이 필요한 경우에는 추론임을 명확하게 표시한다.

---

# 2. ARCHITECTURE.md

`ARCHITECTURE.md`는 다음 질문에 답하도록 작성한다.

> 무엇이 어디에 있으며 어떻게 연결되어 있는가?

최소한 다음 내용을 포함한다.

- 시스템 목적과 범위
- 전체 구성도
- 주요 컴포넌트와 책임
- 컴포넌트 간 인터페이스
- 주요 요청 흐름
- 주요 데이터 흐름
- 데이터 저장소와 데이터 소유권
- 외부 시스템 연동
- 프로세스/서비스/컨테이너 구조
- 네트워크 및 신뢰 경계
- 실행 및 배포 구조
- 중요한 파일과 디렉터리 위치

가능하면 Mermaid 또는 ASCII diagram을 사용한다.

이 문서에서는 구현의 세부 알고리즘보다 시스템의 구조와 경계를 설명하는 데 집중한다.

---

# 3. DESIGN.md

다음 문서를 먼저 읽고 작성 원칙으로 사용한다.

https://raw.githubusercontent.com/zasfe/Labs/refs/heads/master/prompt/design/README.AI.md

그 후 현재 저장소의 실제 구현을 분석하여 `DESIGN.md`를 작성한다.

`DESIGN.md`는 다음 질문에 답하도록 작성한다.

> 왜 이렇게 설계되어 있으며 코드를 변경할 때 무엇을 반드시 이해하고 유지해야 하는가?

단순한 Architecture 문서나 코드 목록을 만들지 않는다.

특히 다음을 찾아 설명한다.

- 시스템의 mental model
- 핵심 설계 아이디어
- 중요한 데이터 구조
- 중요한 알고리즘
- 구현 기법
- invariant
- 상태 전이와 lifecycle
- concurrency 또는 ordering 제약
- 오류 처리 원칙
- 성능상 중요한 결정
- 보안상 중요한 설계 결정
- 선택한 방식의 이유
- 주요 trade-off
- 의도적으로 선택하지 않은 방식
- 변경하면 위험한 부분
- 테스트가 보호해야 하는 설계 조건

가능한 경우 다음 관계가 드러나도록 작성한다.

    Design decision
        ↓
    Implementation
        ↓
    Invariant
        ↓
    Test

코드만 읽어서는 쉽게 알 수 없는 설계 지식을 우선적으로 기록한다.

"무엇을 사용하는가"보다 "왜 사용하는가"를 중요하게 다룬다.

근거가 없는 설계 의도를 만들어내지 않는다. 코드와 테스트만으로 이유를 확인할 수 없다면 `확인되지 않음` 또는 `추론`으로 표시한다.

---

# 4. HANDOFF.md

`HANDOFF.md`는 다음 질문에 답하도록 작성한다.

> 현재 어디까지 진행되었으며 다음 에이전트는 무엇을 해야 하는가?

다음 에이전트가 fresh context 상태에서 이 파일을 읽고 바로 작업을 계속할 수 있어야 한다.

최소한 다음 내용을 포함한다.

- 현재 작업 목표
- 현재 상태
- 지금까지 수행한 작업
- 시도한 방법
- 성공한 방법
- 실패한 방법과 실패 원인
- 현재 확인된 문제
- 미완료 작업
- 다음 작업의 우선순위
- 검증 방법
- 작업 재개에 필요한 명령 또는 파일
- 주의사항

과거의 모든 작업 기록을 축적하는 changelog로 만들지 않는다.

현재 작업을 이어받는 데 필요한 정보만 유지한다.

작업이 완료되거나 상황이 변경되면 오래된 상태를 정리하여 현재 상태를 기준으로 갱신한다.

---

# 5. 세 문서의 책임 분리

내용을 중복해서 복사하지 않는다.

    ARCHITECTURE.md
    └─ 무엇이 어디에 있으며 어떻게 연결되는가?

    DESIGN.md
    └─ 왜 이렇게 설계했으며 무엇을 유지해야 하는가?

    HANDOFF.md
    └─ 현재 어디까지 진행되었으며 다음에 무엇을 해야 하는가?

필요한 경우 다른 문서를 링크한다.

예를 들어 현재 작업에서 발견한 장기적인 설계 원칙은 `HANDOFF.md`에만 남겨두지 말고 `DESIGN.md`에도 반영한다.

시스템 구조 자체가 변경되었다면 `ARCHITECTURE.md`도 갱신한다.

---

# 6. AGENTS.md 연동

기존 `AGENTS.md`를 먼저 확인한다.

기존 규칙을 삭제하거나 전체 파일을 재작성하지 않는다.

적절한 위치에 다음 의미의 규칙을 추가한다.

## 프로젝트 문서 참조 규칙

작업 시작 시 작업의 성격에 따라 다음 문서를 확인한다.

- `ARCHITECTURE.md`: 시스템 구성, 컴포넌트 책임, 인터페이스, 데이터 흐름과 경계를 이해할 때 확인한다.
- `DESIGN.md`: 구현을 추가하거나 변경하기 전에 관련 설계 의도, 데이터 구조, 알고리즘, invariant와 trade-off를 확인한다.
- `HANDOFF.md`: 진행 중인 작업을 이어받을 때 현재 상태, 기존 시도, 문제점과 다음 작업을 확인한다.

구조 변경 시 `ARCHITECTURE.md`, 장기적으로 유지해야 할 설계 결정 변경 시 `DESIGN.md`, 미완료 작업을 다른 에이전트에게 넘길 때 `HANDOFF.md`를 함께 갱신한다.

문서와 실제 코드가 충돌하면 임의로 어느 한쪽을 정답으로 가정하지 않는다. 코드, 테스트, Git history와 관련 근거를 확인하여 원인을 판단하고 필요한 경우 구현과 문서를 함께 수정한다.

---

# 7. 검증

문서 작성 후 다시 실제 저장소와 대조한다.

다음을 확인한다.

1. 존재하지 않는 컴포넌트나 기능을 문서화하지 않았는가?
2. Architecture와 Design을 혼동하지 않았는가?
3. 현재 구현과 문서가 일치하는가?
4. 중요한 invariant가 누락되지 않았는가?
5. 다음 에이전트가 `HANDOFF.md`만으로 현재 작업을 재개할 수 있는가?
6. 새로운 에이전트가 `ARCHITECTURE.md`와 `DESIGN.md`를 읽고 중요한 코드를 안전하게 변경할 수 있는가?
7. 세 문서 사이에 불필요한 내용 중복이 없는가?
8. `AGENTS.md`의 기존 지침을 훼손하지 않았는가?

마지막으로 생성 또는 수정한 파일 목록과 각 파일에서 기록한 핵심 내용을 간략하게 보고한다.
