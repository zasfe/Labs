# Codex 토큰 효율 및 서브에이전트 운영 규칙

- 문서 버전: 1.1 / 2026-09-10
- 용도: 다른 사용자의 Codex가 분석하고 선택적으로 도입할 수 있는 독립형 참고 문서
- 범위: 컨텍스트·반복 실행 비용 절감, 서브에이전트 수·모델·권한·자료 교환 관리

기존 개인 운영 규칙에서 위 두 영역만 추려 중복을 통합했습니다. 개인 프로필, 회사·프로젝트 정보, 장치 경로, 인증, 세션 기록, 플러그인 설정은 포함하지 않습니다. 특정 절감률이나 모델 지원 여부를 보장하는 문서가 아니며, 토큰 사용량·응답 시간·로컬 로그 용량은 서로 다른 지표입니다.

## 1. 이 문서를 전달받은 Codex에게

먼저 현재 사용자의 목적과 기존 지침에 맞춰 이 규칙을 분석합니다. 참고 자료를 읽으라는 요청만으로 전역 설정을 변경하지 않습니다. 사용자가 적용까지 요청했다면 그 승인 범위에서 기존 지침과 차이를 대조하고, 변경 파일을 백업한 뒤 필요한 조항을 병합합니다. 이미 승인된 같은 범위를 반복해서 확인하지 않습니다.

원본의 숫자 제한은 운영 기본값으로, 모델명과 실행 옵션은 환경 의존 참고값으로 구분합니다. 대상의 실제 모델 목록, 서브에이전트 도구, 동시 실행 상한, 파일 접근 방식이 다르면 해당 부분을 조정하고 이유를 설명합니다. 이 문서는 시스템·개발자·보안·도구 제약이나 대상 사용자의 명시적 지시보다 우선하지 않습니다.

원본 파일이나 별도 스킬 설치 없이 아래 내용만으로 검토할 수 있습니다. 전역 지침을 간결하게 유지하려면 상시 적용 핵심만 루트 지침에 두고, 상세 규칙은 위임·대용량 자료 교환 등 해당 작업을 시작할 때 참조하도록 구성합니다. 문서가 존재한다는 사실만으로 자동 로딩이나 강제가 구현됐다고 보고하지 않습니다.

## 2. 토큰과 컨텍스트 사용

### 실제 config의 자동 압축 기준

다음은 2026-09-10 원본 시스템의 사용자 설정에서 직접 확인한 두 항목입니다. 개인 경로나 인증 정보 없이 설정값만 추출했습니다.

```toml
model_auto_compact_token_limit = 220000
model_auto_compact_token_limit_scope = "body_after_prefix"
```

- `model_auto_compact_token_limit`: 대화 기록의 자동 컨텍스트 압축을 시작하는 기준을 220,000토큰으로 지정합니다. 누적 사용량·과금·출력 길이를 제한하는 하드 상한이 아니며, 전체 컨텍스트가 항상 22만 토큰 이하라는 뜻도 아닙니다.
- `model_auto_compact_token_limit_scope`: 기준을 계산할 범위를 지정합니다. `body_after_prefix`는 이어받은 압축 윈도우의 보존된 접두사 이후 증가분을, 기본값인 `total`은 활성 컨텍스트 전체를 계산 대상으로 삼습니다. 접두사를 단순히 캐시된 토큰 전체나 전역 지침 전체와 동일시하지 않습니다.

옵션 정의는 [OpenAI 공식 설정 참조](https://learn.chatgpt.com/ko-KR/docs/config-file/config-reference)를 기준으로 확인했습니다. 220,000은 원본 사용자의 선택값이지 모든 모델·작업에 대한 권장값이 아닙니다. 이 설정은 컨텍스트 관리 수단이며, 압축 자체의 처리 비용과 정보 손실 가능성까지 고려해야 하므로 토큰 절감을 보장하지 않습니다.

대상 Codex의 적용 절차:

1. 현재 버전이 두 키와 `body_after_prefix` 값을 지원하는지 확인하고, 사용 모델의 컨텍스트 한도와 기존 압축 설정을 대조합니다. 지원 여부가 불명확하면 임의로 대체하거나 적용 성공으로 보고하지 않습니다.
2. 사용자가 적용을 승인한 범위에서 대상의 실제 사용자 설정 파일을 찾아 백업합니다. 사용자 지정 `CODEX_HOME`과 프로필·실행 인수에 의한 재정의 여부도 확인합니다.
3. 기존 키가 있으면 수정하고, 없으면 TOML 최상위 영역에 병합합니다. 표준 사용자 설정에 위 예시를 넣을 때는 첫 `[section]` 선언 앞에 배치하여 다른 섹션의 값이 되지 않게 합니다. 전체 설정을 덮어쓰거나 모델·권한·인증 설정을 함께 이식하지 않습니다.
4. 새 실행에서 설정 인식과 오류 여부를 확인합니다. 실제 압축 시점은 정상 작업 중 관찰하며, 검증만을 위해 22만 토큰의 입력을 생성하지 않습니다. 설정 파일 확인과 실제 압축 동작 검증은 구분해 보고합니다.

이 문서 작성에서는 원본 값과 공식 정의만 확인했으며, 대상 시스템에서의 적용이나 압축 실행은 검증하지 않았습니다.

### 필요한 근거만 읽고 재사용

- 현재 목적에 필요한 파일·구간·로그를 우선 탐색합니다. 편의를 위해 전체 저장소, 모든 규칙, 장문 로그나 무관한 문서를 대화에 넣지 않습니다.
- 이미 읽었고 변경되지 않은 근거와 참조를 재사용합니다. 규칙 전체를 매 턴 다시 읽지 않습니다.
- 컨텍스트 압축 또는 불확실한 재개 후에는 최신 사용자 지시, 적용 규칙, 현재 작업 상태와 쓰기 권한을 실제 자료에서 다시 확인합니다. 요약에 남은 오래된 계획만으로 실행하지 않습니다. 필요한 재확인을 토큰 절약 때문에 생략하지 않습니다.
- 검색·조회 결과는 판단에 필요한 범위로 제한합니다. 큰 중간 결과는 파일에 보존하고 대화에는 결론, 근거 위치, 중요한 예외만 전달합니다.
- 답변·보고서·위임 요약은 요청 목적을 이해할 만큼 자립적으로 작성합니다. 짧게 만들기 위해 핵심 근거, 실패, 불확실성이나 다음 행동을 삭제하지 않습니다.

### 반복 작업과 불필요한 산출물 제한

- 독립적인 조회는 묶어서 병렬 실행할 수 있습니다. 병렬화는 대기 시간을 줄일 수 있지만 호출량이나 토큰 사용량이 자동으로 감소한다는 뜻은 아닙니다.
- 관련 편집과 기능 검증은 의존성이 허용하는 범위에서 한 묶음으로 처리합니다. 배치 작업은 대략 3~7개 단위의 점검 지점으로 나눕니다.
- 작은 함수마다 테스트하거나 매 편집 직후 전체 diff를 확인하지 않습니다. 파일·기능 단위로 영향 범위에 맞게 검증하되, 불확실하거나 공유 동작에 영향을 주는 변경은 즉시 확인합니다.
- 하나의 주 작업 흐름을 선택합니다. 서로 다른 필수 기능이 있을 때만 보조 스킬을 추가하고, 동등한 리뷰·문장 다듬기·검색을 중복 적용하지 않습니다.
- 일상적인 자기 점검과 비판적 판단을 별도 다중 에이전트 리뷰의 자동 호출 조건으로 삼지 않습니다. 요청 범위에 없는 보고서, 이미지, 보드, 추가 형식이나 외부 게시를 만들지 않습니다.
- 명시적으로 선택된 작업 흐름의 필수 품질 검증은 유지합니다. 비용 절약을 이유로 이미 합의된 독립 검수나 완료 조건을 조용히 완화하지 않습니다.

## 3. 검증 강도와 재시도

검증·반복 노력은 사용자에게 보이는 영향, 실패 위험, 변경의 되돌리기 가능성, 실제 사용 목적에 비례시킵니다. 추가 수정의 실익이 작으면 종료하되, 명시된 필수 요건은 충족해야 합니다.

| 상황                                            | 행동                                                                                                                        |
|-------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|
| 같은 접근이 연속 두 번 실패                     | 해당 접근을 중단하고 관측 근거에 따라 전략을 바꾸거나 현재 결과를 제시                                                      |
| 접근을 바꿔도 같은 목표에서 세 번째 실패        | 추가 재시도를 잠시 멈추고 원인·현재 결과·다음 선택의 비용과 사용자 판단 필요성을 평가                                       |
| 세 번째 실패 이후 계속할 근거가 있음            | 사용자의 방향 지시가 있거나, 이미 허용된 범위의 명확히 다른 저비용·저위험 비추측적 조치가 있을 때 진행. 그 근거를 먼저 설명 |
| 실질적인 시각 생성·편집이 두 번 만족스럽지 못함 | 최선의 후보를 실제 사용 크기와 한계와 함께 보여주고, 다음 생성 전에 방향을 확인                                             |
| 요구사항·프로토콜에 따른 작업을 완료            | 필수 조항과 결과를 대조하고 관련 진입점의 낡거나 충돌하는 지침을 점검                                                       |

같은 목표를 향한 프롬프트 미세 수정, 인수 변경, 단계 이름 변경은 실패 횟수를 초기화하지 않습니다. 전략 변경도 목표 단위 실패 기록을 지우지 않습니다.

시각 작업은 실제 표시 크기에서 먼저 확인하고, 사용자가 식별하기 어려운 차이를 위해 무제한 재생성하지 않습니다. 기존 결과를 허용된 결정적 변환이나 제한된 수정으로 개선할 수 있으면 우선 검토합니다. 원본과 사용자 변경은 보존합니다.

완료 검수는 일관된 작업 묶음에 대해 한 번 수행하고, 수정 후에는 해당 요건과 영향받는 의존성을 다시 확인합니다. 새로운 변경·실패·미해결 우려가 없으면 전체 검증을 반복하지 않습니다. 파일 검사 통과, 실제 실행 성공, 사용자 관점의 결과를 구분합니다.

## 4. 서브에이전트 생성과 수명 관리

서브에이전트는 독립적이고 범위가 정해진 작업에서 품질·범위 점검·속도·컨텍스트 분리에 실익이 있을 때 사용합니다. 작은 작업이나 순차 의존성이 큰 작업은 주 에이전트가 수행합니다. 충분하다면 1~2개만 사용합니다.

| 항목                                  | 원본 운영 기본값                                                  |
|---------------------------------------|-------------------------------------------------------------------|
| 한 사용자 요청에서 새로 생성하는 총수 | 주 에이전트를 제외하고 최대 3개                                   |
| 동시 실행 수                          | 최대 3개이면서 실제 런타임 상한 이내                              |
| 종료한 에이전트                       | 총 생성 수에서 차감하지 않음                                      |
| 기존 에이전트에 후속 요청             | 새 생성으로 세지 않고 적합한 작업이면 재사용                      |
| 중첩 위임                             | 기본 금지. 사용자가 명시한 범위에서만 허용                        |
| 일회성 CLI/helper와 하위 위임         | 같은 총수·모델·권한 기준에 포함                                   |
| 추가 생성 요청                        | 사용자가 명시한 추가 수와 범위만 허용. 실제 동시 실행 상한은 유지 |

도구나 실행 경로를 바꾸거나 라운드·단계 이름을 바꿔 수량 제한을 우회하지 않습니다. 추가 에이전트 승인은 고비용 모델 사용 승인이나 중첩 위임 승인이 아닙니다. 동시 실행 한도보다 많은 작업이 승인됐다면 필요한 작업을 순차 실행합니다.

독립 검수에 새 에이전트가 필요하면 탐색·생성 전에 검수용 수량을 확보합니다. 남은 수량이 부족하면 필요한 추가 범위를 설명하고, 검수 조건 자체를 축소하지 않습니다.

더 이상 도움이 되지 않는 에이전트는 중지·종료합니다. 실패한 에이전트를 새로 만들기 전에 작업 범위를 좁히거나 접근을 바꿉니다. 기본은 읽기 중심의 독립 조사와 한 명의 주 작성자이며, 여러 작성자가 필요하면 파일·모듈별 쓰기 소유권을 명확히 나눕니다.

## 5. 모델·추론·권한 선택

부모 모델과 추론 수준을 묵시적으로 상속하지 않습니다. 각 에이전트의 작업 난도에 맞는 모델과 추론 수준을 명시하고, 실행 도구에서 실제로 지원하는지 확인합니다.

원본에서는 일반 작업에 Sol/high, 기계적 검사·분류에 Luna/low, 제한된 탐색·로그 분석에 Terra/low~medium을 사용합니다. Astra는 특별히 복잡한 판단에 medium~high를 제안하되 명시 승인 대상으로 두었습니다. 이 이름과 수준은 원본의 선택 예시이며 동료 계정에 그대로 강제할 값이나 최신 지원 목록은 아닙니다. 대상에서는 일상용·경량용·고비용 예외용 모델의 역할과 승인 경계를 맞춰 적용합니다.

- 사용자가 이미 선택한 주 세션 모델은 유지합니다. 고비용 모델의 주 세션을 선택했다는 사실만으로 같은 모델의 자식 에이전트까지 승인된 것은 아닙니다.
- 고비용 예외 모델에는 목적·작업 범위·에이전트 수·추론 수준의 명시 승인을 적용합니다. 이미 해당 작업이 승인됐다면 같은 범위의 후속 실행에 승인을 반복 요청하지 않습니다.
- 추가 수량, 다른 목적, 범위 확대, 승인된 추론 수준을 넘는 실행은 별도 범위로 취급합니다. medium~high 승인을 max/ultra 등으로 확대하지 않습니다.
- 난도가 높음, 남은 사용량, 긴급성, 사용자의 침묵이나 일반적인 자율 실행 지시는 고비용 모델의 자동 호출 근거가 아닙니다. 지원되지 않는 모델을 고비용 모델로 조용히 대체하지 않습니다.
- helper 경로를 만들거나 바꿀 때는 모델·추론·작업 디렉터리·결과 위치·읽기/쓰기 범위의 유효 설정을 확인합니다. 모든 일반 작업마다 전체 실행 경로를 검사할 필요는 없습니다.
- 조회 전용 작업에는 가능한 도구 수준의 읽기 전용 권한을, 파일 생성 작업에는 승인된 출력 영역의 쓰기 권한을 사용합니다. 프롬프트의 '읽기 전용' 문구는 기술적 샌드박스가 아닙니다.
- 호출별 권한 제어가 없으면 그 한계를 밝히고 승인된 범위를 행동으로 지킵니다. 미지원 옵션을 만들거나 전역 권한을 낮춰 우회하지 않습니다.

## 6. 컨텍스트를 최소화한 위임과 검수

각 에이전트에는 목표, 제약, 읽을 자료, 허용된 쓰기 경계, 완료 조건과 반환 형식을 담은 짧고 자립적인 작업 지시를 전달합니다.

- 부모 대화가 필요하지 않으면 대화 이력을 상속하지 않습니다. 원본 도구의 `fork_turns="none"`은 이 의도를 표현한 예시입니다. 대상 도구에 같은 옵션이 없으면 지원되는 새 컨텍스트와 최소 입력 전달 방식으로 조정합니다.
- 정확한 최근 문장이 꼭 필요할 때만 큰 자료가 없는 최소 턴을 전달합니다. 편의를 위해 전체 대화·저장소·로그를 복제하지 않습니다.
- 반환은 결론, 핵심 근거, 파일 위치, 남은 불확실성과 필요한 다음 행동으로 제한합니다. 원시 중간 출력은 요청되거나 판단에 필요한 경우에만 포함합니다.
- 검수자는 요약만 검증하는 역할이 아닙니다. 승인된 읽기 범위 안에서 원본과 반대 근거를 표적 확인할 수 있어야 합니다. 작성자가 고른 발췌만으로 결론을 강요하지 않습니다.
- 조회 실패나 접근 불가는 부재의 증거가 아닙니다. 중요한 판단에는 검색 범위와 접근 한계를 함께 보고합니다.

위임 지시 예시:

```text
목표: 지정 모듈의 변경으로 생길 수 있는 회귀를 검토한다.
읽기 범위: 제공한 파일과 주장을 확인하는 데 필요한 승인된 직접 참조.
쓰기 범위: 없음.
모델/추론: 대상에서 확인한 일상용 모델과 작업에 맞는 수준을 명시.
대화 상속: 없음. 필요한 변경 요약과 원본 경로만 전달.
완료 조건: 영향받는 경로의 근거를 제시하고 검증 실패와 결함을 구분.
반환: 중요한 발견, 근거 위치, 미검증 범위. 원시 로그 재전송 금지.
```

## 7. 대용량 파일과 이미지 교환

이미지·오디오·영상·PDF·압축파일·데이터셋 등 큰 자료는 공유 가능한 작업 파일로 보관합니다. 에이전트 간 메시지에는 파일 위치와 필요한 메타데이터를 전달합니다. 대상들이 같은 파일에 접근할 수 없는 환경이면 지원되는 파일 전달 방법을 먼저 확인합니다.

- 작업별 input/output 영역이나 이미 존재하는 불변 자료를 사용합니다. SHA-256이 같은 파일은 중복 생성하지 않습니다. SHA-256은 파일 내용의 동일성 확인용 값입니다.
- 필요한 경우 절대 경로, SHA-256, 파일 형식, 바이트 크기, 이미지 크기/재생 시간, 출처, 참조 역할, 검사 목적을 전달합니다. 매번 모든 필드를 강제하지는 않습니다.
- 원본은 불변으로 취급하고 수정 결과는 새 버전 파일로 저장합니다. 수신자는 필요한 최소 파일을 읽고, 같은 내용이면 불필요하게 다시 열지 않습니다.
- 경로로 충분한 경우 Base64, data URL, 중복 첨부, 이진 데이터를 포함한 전체 도구 결과를 지시문·요약·로그·JSON·반환 메시지에 복제하지 않습니다.
- 이미지가 많은 부모 세션에서는 전체 이력을 상속하지 않습니다. 공통 시각 확인은 주 에이전트가 한 번 수행해 텍스트로 전달하고, 독립 픽셀 검수가 필요할 때만 해당 에이전트가 최소 이미지를 열도록 합니다.
- 검수자는 텍스트 발견과 결과 파일 위치를 반환합니다. 확인했다는 이유로 원본 이미지나 이진 자료를 다시 첨부하지 않습니다. 일회성 시각 CLI 검사도 에이전트 수와 모델 승인 기준에 포함합니다.
- 로컬 파일 교환은 반복 복제를 줄이지만 내부 세션 로그에 이미지가 전혀 기록되지 않음을 보장하지 않습니다. 사용량을 줄이려는 목적으로 활성 세션 로그를 후처리해 이미지 데이터를 제거·치환하지 않습니다.

## 8. 채택 후 확인과 적용 범위

첫 적용에서는 실제로 필요한 작은 작업을 통해 총 생성 수, 동시 실행 수, 명시된 모델·추론·권한, 컨텍스트 상속 범위, 중복 읽기·자료 재전송, 쓰기 충돌을 확인합니다. 문서를 공유받았다는 이유만으로 검증용 에이전트나 고비용 호출을 생성하지 않습니다.

절감 효과를 평가하려면 유사 작업에서 입력·출력 사용량, 재시도 수와 에이전트 수를 비교합니다. 측정 없이 절감률을 추정값 이상으로 제시하지 않습니다. 대기 시간 감소나 로그 파일 축소를 토큰 절감과 동일시하지 않습니다.
